# Правила React-кода студии: что перенесено из чужой практики и почему

Источник — каталог правил производительности React и Next.js от Vercel Engineering
(`vercel-labs/agent-skills`, `react-best-practices`, MIT). Каталог написан под Next.js с серверной
отрисовкой; студия — одностраничное приложение на Vite, которое ходит к серверу через одну дверь
`studio/app/mcp/`. Поэтому правило берётся не по заголовку, а по вопросу «сработает ли у нас», и
ответ проверяется замером на нашем дереве. Здесь пересказ своими словами с нашими примерами.

Оглавление: как читать · запросы к серверу · вес бандла · перерисовки · отрисовка · JavaScript ·
что не переносится · как проверять.

## Как читать

Каждое правило помечено: **как есть** — работает в студии без изменений; **с заменой** — суть та же,
механизм наш; **замерено** — проверено на собранном дереве, и написано, что показал замер.

## Запросы к серверу (у Vercel — «водопады»)

У Vercel это серверные компоненты; у нас то же самое происходит в экране, читающем несколько листов
через дверь.

- **Независимые чтения — параллельно** (как есть). Экран канала, которому нужны видео, сценарии и
  статистика, не ждёт одно чтение, чтобы начать следующее: `Promise.all` в слое доступа, а не
  цепочка `await` в экране.
- **`await` — там, где значение нужно** (как есть). Чтение, нужное только в одной ветке, не
  блокирует остальные.
- **Дешёвая проверка до дорогого ожидания** (как есть). Нет выбранного канала — не ходим за его
  видео вовсе.
- **Склейка одинаковых запросов** (с заменой: у Vercel — SWR). Две части экрана, читающие один лист,
  дают один запрос. Механизм — кеш чтений библиотекой (`references/performance.md`), а не своя
  карта промисов.
- **Граница `Suspense` вокруг медленной части** (с заменой: у нас без потоковой отрисовки). Экран
  показывает готовое сразу, а медленный блок — своё состояние загрузки (домен `студия-общее`).

## Вес бандла

- **Экран домена — по требованию** (с заменой: `next/dynamic` → `React.lazy` + `Suspense`).
- **Модуль, нужный только при включённой функции, грузится при её включении** (как есть):
  `import()` внутри обработчика, например тяжёлый редактор сценария.
- **Предзагрузка по наведению или фокусу** (как есть): `import()` экрана на `onPointerEnter`/
  `onFocus` ссылки навигации делает переход мгновенным без веса на старте.
- **Импорт из «бочки» (barrel)** (замерено). В собранной студии Vite вытряхивает неиспользуемое:
  из всей библиотеки иконок в бандл попадают только импортированные. Для размера бандла правило у
  нас ничего не даёт, выигрыш только в скорости сервера разработки. Держим именованные импорты, но
  переписывать импорты «ради веса» не нужно.
- **Пути импорта — статически разбираемые** (как есть): `import(\`./screens/${name}\`)` сборщик не
  разрежет, и в бандл поедут все экраны.
- **Сторонние скрипты после первой отрисовки** (с заменой): у нас их нет и не должно быть без
  решения владельца (`security-reviewer`, внешние получатели).

## Перерисовки

- **Производное — при отрисовке, а не эффектом** (как есть; подробно — `no-unnecessary-effects`).
- **Логика взаимодействия — в обработчике, а не в эффекте**, реагирующем на смену состояния (как
  есть). Эффект «сохранить, когда изменилось» ломает правило одной записи на жест.
- **Подписка на производный флаг, а не на сырое значение** (как есть): компонент, которому нужно
  «список пуст?», не перерисовывается на каждый новый элемент.
- **Не читать состояние, которое нужно только в обработчике** (как есть): его берут в момент
  события, а не держат подпиской.
- **Функциональный `setState`** (как есть): `setItems(prev => …)` — обработчик стабилен и не
  захватывает устаревшее значение.
- **Ленивая инициализация `useState(() => …)`** (как есть) для дорогого начального значения.
- **Компонент не объявляется внутри компонента** (как есть): такой компонент пересоздаётся на каждую
  отрисовку и теряет состояние и фокус — у ИИ это частая ошибка при «выносе куска разметки».
- **Несрочное — в `startTransition`, тяжёлый список — через `useDeferredValue`** (как есть).
- **Частое переходное значение — в `ref`**, а не в состоянии (как есть): позиция курсора при
  перетаскивании не перерисовывает дерево; в состояние попадает итог жеста по отпусканию.
- **Ручная мемоизация** (с заменой). У Vercel — вынести тяжёлое в `memo`-компонент и не мемоизировать
  простое. У нас сначала замер профилировщиком; если в сборку войдёт React Compiler, ручные `memo`
  становятся шумом. Не мемоизировать простые выражения — как есть.
- **Зависимости эффекта — примитивы**, а не объекты, создаваемые при отрисовке (как есть).

## Отрисовка

- **Длинный список — `content-visibility: auto`** для блоков вне экрана (как есть; пол браузеров это
  держит), а для очень длинных — окно отрисовки библиотекой.
- **Условная отрисовка — тернарным оператором, а не `&&`** (как есть): `{count && <Badge/>}` рисует
  `0` на экране, когда счётчик нулевой.
- **Статичная разметка — вне компонента** (как есть): константа JSX не пересоздаётся.
- **Анимировать обёртку, а не `<svg>`** (как есть): у SVG-элемента нет аппаратного ускорения во
  многих браузерах.
- **Показ и скрытие без потери состояния** (с заменой: `<Activity>` из React 19.2): вкладки канала,
  которые должны помнить прокрутку и ввод, скрываются, а не размонтируются.
- **Подсказки загрузки ресурсов** (как есть): `preload` для шрифта и картинки первого экрана через
  API React DOM.

## JavaScript

Переносится как есть, но применяется только там, где профилировщик показал горячее место:
`Map`/`Set` для повторных поисков (сопоставление каналов с сетками), один проход вместо цепочки
`filter().map()` на больших списках, ранний выход, регулярное выражение вне цикла, `toSorted()`
вместо мутирующей сортировки состояния, `requestIdleCallback` для несрочной работы. Микро-правка
без замера не принимается (`references/performance.md`, «чего не делать»).

## Что не переносится

- Серверные компоненты, `React.cache`, сериализация пропсов на сервер, `after()`, серверные
  действия, подавление ошибок гидрации — у студии нет серверной отрисовки. Их суть («сервер не
  делает лишней работы и не отдаёт лишних данных») живёт на стороне MCP-сервера, а не в студии.
- SWR как библиотека — выбор кеша чтений один на студию, и это решение `dependency-hygiene`.

## Как проверять, что правило сработало

Правка «по правилу» принимается с числом до и после, иначе это ритуал:

- вес — вывод `npm --prefix studio run build`;
- перерисовки — профилировщик React DevTools (что перерисовалось и почему);
- отклик жеста — вкладка Performance браузера, длинные задачи;
- экран на устройствах — `scripts/devices.mjs`.

Правило, не давшее измеримого эффекта на нашем дереве, отмечается «замерено» с результатом — как
правило про импорт из «бочки» выше, — чтобы следующая сессия не переписывала код ради него.
