# Стандарты платформы студии: скорость · экраны · браузеры · доступность

Студия уходит в продакшен, и пользователь увидит её не в той ширине и не в том браузере, где её
собирали. ИИ проверяет вёрстку на одном экране и в одном движке, мышью и без скринридера — и
всё, что за этими пределами, ломается молча. Этот скил — нормы, которые держатся ЗАМЕРОМ, и
команда для каждого замера.

Три правила, общие для всех четырёх осей:

1. **Порог — внешний и с источником**, наш — объявлением в репозитории. Число «на глаз» в
   компоненте — хардкод (`anti-hardcode`); число «из головы» в ревью — мнение.
2. **Механизм — из библиотеки** (`code-quality`, ось 1a): фокус-ловушку, вкладки, диалог,
   виртуальный список, кеш запросов свои не пишем. Условие отбора владельца: библиотека без
   API-ключей и без внешнего получателя данных; поставка npm — `dependency-hygiene`.
3. **Проверено = прогнано в браузере.** `tsc` и `eslint` не видят ни ширины, ни фокуса, ни веса
   бандла. Слова «адаптивно» и «доступно» без прогона не принимаются.

## Скорость — `references/performance.md`

Цель — «хорошо» по Core Web Vitals на 75-м перцентиле: LCP ≤ 2.5 с, INP ≤ 200 мс, CLS ≤ 0.1 <!-- снимок ок: внешний порог web.dev/articles/vitals -->.
Что чаще всего стоит студии скорости:

- **весь экран в одном бандле** — домены студии грузятся по требованию (`React.lazy` на экран
  домена), а не одним файлом;
- **иконки целиком** — `lucide-react` только именованным импортом; «иконка по имени строкой» тянет
  всю библиотеку;
- **перерисовка всего дерева** — состояние в корне (как в дизайне) перерисовывает всё на каждое
  нажатие клавиши; состояние живёт там, где читается;
- **`transition-all`** анимирует и раскладку; анимировать только `transform` и `opacity`;
- **картинки без размеров** — сдвиг раскладки (CLS); у миниатюры всегда `width`/`height` или
  `aspect-ratio`, ниже первого экрана — `loading="lazy"`;
- **сотни узлов списка** — окно отрисовки для длинных списков видео и комментариев;
- **повторные чтения сервера** — кеш чтений с инвалидацией по записи; своего кеша не пишем.

Правила React-кода (запросы, бандл, перерисовки, отрисовка) с пометкой, что переносится из
чужой практики как есть, что с заменой, а что замерено и не дало эффекта, —
`references/react-rules.md`.

Замер — сборка печатает вес чанков; бюджет объявляется и держится храповиком, а не памятью:

```bash
npm --prefix studio run build
```

## Экраны — `references/screens-browsers.md`

- **Mobile-first**: класс без префикса — узкий экран, `sm:`/`md:`/`lg:` добавляют.
- **Матрица ширин**, на которой гоняется геометрия (наложение, выход текста, уход за край):
  320 · 390 · 768 · 1024 · 1280 · 1920 <!-- снимок ок: матрица ширин — правило, нижний край из WCAG 1.4.10 -->.
  Сегодня геометрия стенда гоняется на одной ширине — это не «адаптив проверен».
- **Посмотреть глазами устройства** — снимки всей страницы на профилях телефона, планшета и
  монитора плюс наложение, выход за край, прокрутка вбок и мелкие цели касания на каждом:
  ```bash
  npm --prefix studio run build
  node .claude/skills/studio-web-standards/scripts/devices.mjs
  ```
  Снимок открывается инструментом чтения картинок — ИИ видит экран, а не угадывает его. Это
  эмуляция устройства в Chromium, а не Safari: причуды WebKit ловит только матрица движков.
- **Компонент, живущий в разных ширинах** (карточка в сетке и в выдвижной панели), подстраивается
  под КОНТЕЙНЕР (`@container`), а не под окно.
- **`hover:` в Tailwind v4 срабатывает только на устройствах с наведением** — кнопка, появляющаяся
  по наведению, на телефоне не появится НИКОГДА. У каждого действия есть путь без наведения.
- **`min-h-screen` на телефоне врёт** (панель браузера): `min-h-dvh`; отступы под вырез —
  `env(safe-area-inset-*)`.
- **Флекс-ребёнок с длинным текстом** вылезает из-за `min-width: auto`: `min-w-0` + перенос слов.

## Браузеры — `references/screens-browsers.md`

**Пол поддержки объявляется ОДИН раз и один для всех инструментов.** Tailwind v4 сам задаёт пол
(Safari 16.4 · Chrome 111 · Firefox 128 <!-- снимок ок: внешний порог, tailwindcss.com/docs/compatibility -->),
и он выше цели сборки Vite по умолчанию: значит реальный пол — тайлвиндовский, и `browserslist`,
`build.target` и `lib` TypeScript обязаны с ним совпадать. API выше пола (`Object.groupBy`,
`popover`) типизируется без ошибок и падает в Safari у пользователя — ловит линтер совместимости по
`browserslist`, а не память.

Движки — три: Chromium (Chrome, Edge, Яндекс Браузер), WebKit (Safari и все браузеры iOS), Gecko
(Firefox). Прогон геометрии и доступности — во всех трёх проектах Playwright.

## Доступность — `references/accessibility.md`

Норма — WCAG 2.2 уровня AA. Минимум, который ИИ ломает чаще всего:

- **фокус виден всегда**: `outline-none` без `focus-visible:`-кольца — удалённая клавиатура;
- **действие — `button`, переход — `a href`**; `div` с `onClick` недоступен с клавиатуры;
- **диалог**: роль, фокус внутрь, `Escape`, возврат фокуса, фон инертен — нативный `<dialog>` или
  библиотека, а не самописная ловушка;
- **вкладки** (канал, видео-проект) — шаблон WAI-ARIA Tabs со стрелками;
- **иконка-кнопка** без текста — с доступным именем;
- **контраст пар токенов** — текст 4.5:1, крупный текст и элементы управления 3:1 <!-- снимок ок: внешний порог WCAG 2.2 1.4.3 и 1.4.11 -->;
  цвет не единственный носитель смысла (статус — ещё и словом);
- **асинхронный статус** (сохранено, рендер идёт) объявляется `role="status"`;
- **движение** уважает `prefers-reduced-motion` (`motion-safe:`/`motion-reduce:`).

Контраст пар токенов меряется по объявлению, а не глазами:

```bash
python3 .claude/skills/studio-web-standards/scripts/contrast.py studio/app/tokens.css
```

Автоматический прогон (`axe-core` через Playwright) ловит только часть нарушений; проход
клавиатурой по экрану — обязателен руками, пока его нет в наборе.

## Как это становится приёмкой

Каждая норма здесь — кандидат в условие предмета `студия-платформа` в
`scripts/guards/acceptance_subjects.yaml`; состояние печатает `invariants.py --приёмка`. Норма,
ставшая механизмом (матрица ширин в Playwright, линтер совместимости, `axe`, бюджет бандла), уходит
в гейт `studio-app` — тогда и только тогда она «судится».

## Границы

- `studio-acceptance` — сломала ли правка студию и верна ли она домену; здесь — держит ли студия
  нормы платформы.
- `frontend-design` — замысел вида; здесь — чтобы замысел работал на любом экране и для всех.
- `security-reviewer` — разметка из недоверенных данных, CSP, внешние получатели.
- `dependency-hygiene` — можно ли тянуть библиотеку, которую здесь советуют.
- `no-unnecessary-effects` — эффект как причина лишних перерисовок.
- `code-quality` — механизм из библиотеки вместо своего кода (ось 1a).
