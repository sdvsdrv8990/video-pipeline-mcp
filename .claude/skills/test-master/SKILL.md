# Test Master — video_pipeline_mcp

Тест-специалист **этого** проекта: pytest, симуляционные/adversarial-тесты против `core/firewall`, регрессии на закрытые `D#`, покрытие по `docs/roadmap/03_testing_plan.md`. Проверяет контракты (`ToolResult`/`ErrorDetail`) и коды `server_reactions`.

Стек — **Python + pytest**. Jest/k6/Playwright не применяются.

## Конвенции проекта (жёстко)

- **Симуляционные/adversarial-тесты — первый класс.** Они симулируют атаки из `docs/roadmap/06_threat_catalog.md` и проверяют, что `core/firewall` их ловит **и подключён** (регрессия на D8 «мёртвое правило», D2 «конфиг не загружен»).
- **Регрессия на каждый закрытый D#.** Починили дефект (напр. D1 path traversal) → тест, воспроизводящий эксплойт, который теперь должен падать у атакующего. Тест ссылается на `D#`.
- **Ассерты — на контракт.** Проверять `ToolResult.status/error/facts`, тип `ErrorDetail`, конкретный код `server_reactions` — не «truthy», а точный исход.
- **Docstring теста — ТЕРСОВЫЙ**: одна строка «что проверяет» (+ `D#` для регрессии). НЕ вписывать «5 вопросов»/D#-эссе/историю «прежде было X» в код — это в commit + `docs/roadmap/_sessions.md` (анти-паттерн «process-нарратив в коде»).
- **Философия (жёстко):** тест = **сценарий реального поведения**, не проверка кода. Простые mock-only тесты «куда попало» — **запрещены**.
- **Размещение (свод — memory `project-rules` §3, `~/.claude/projects/-home-admin-projects-video-pipeline-mcp/memory/project-rules.md`):** быстрый → `tests/quick/` (создал → запустил → **удалил**, кроме регрессий `test_audit_fixes`/`test_tunnel`); постоянный → `tests/<name>/test_<name>.py` + `history.md`. **Никогда** не класть тест вне `tests/` по структуре / рядом с кодом / «на потом».
- **Реальный запуск (обязательно для поведенческих):** тест бьёт по **живому серверу** — `aiohttp` POST JSON-RPC 2.0 на `http://127.0.0.1:$MCP_SERVER_PORT/mcp`, ассерт по реальному ответу (`ToolResult`/код реакции). Мок — **только** истинно внешние провайдеры (litellm/stable-ts облако), **никогда** как замена запуску сервера.
- **Изоляция.** Тесты независимы и не зависят от порядка (firewall хранит состояние — сбрасывать между тестами).
- **Тестируем поведение, не реализацию** (кроме проверки «правило реально вызвано» — это как раз про проводку).
- **Эталон не вписывается руками, если он вычислим.** Число, поставленное в ассерт однажды (`== 36` строк-дефолтов, `== 67` инструментов, длина списка), краснеет на ЛЕГИТИМНОМ добавлении: ловит не дефект, а сам факт изменения — цена ему ложная тревога и соблазн «просто поправить число». Порядок выбора: **(1)** посчитать ожидаемое **из источника истины прямо в тесте** (`sum(len(s["rows"]) for s in schema["sheets"])`) — тогда проверяется требование («все дефолты доехали в книгу»), а не совпадение с памятью автора; **(2)** не вычислимо (контракт целиком) → **сгенерированный эталон** рядом с набором + обновление явным флагом, чтобы diff попадал в ревью — образец в проекте: `tests/quick/test_tools_inventory.py` + `tools_inventory.golden.json`, `--bless`; **(3)** жёсткое число — только когда САМО число есть требование (порог, `max_fallback_depth: 5`), и тогда читается из конфига. Вопрос на ревью: «что покраснеет, если осознанно добавить сюда ещё одну строку?» Если тест, а не поведение — эталон выбран неверно.

- **Ассерт по ключу, которого ты не видел, — пустой ассерт.** `{i.get("issue") for i in issues}` при реальном
  ключе `type` даёт `{None}` и проходит ВСЕГДА. Правило: сначала распечатай одну запись целиком, потом
  ассертируй по её ключам; в сообщение подставляй ФАКТИЧЕСКОЕ значение. Увидел в выводе зелёного теста
  `(None)`, `([])`, `(—)` там, где ждал содержимое, — ассерт не проверяет ничего, чини его, а не радуйся.
- **Уровень вызова выбирается по тому, ГДЕ живёт дефект.** `_eng.tools[name].handler(**kw)` зовёт хендлер
  мимо диспетчера: если дефект в диспетчере (обезличивание кода реакции в `INTERNAL_ERROR` — `F95`), такой
  тест его не увидит и будет зелёным на сломанном сервере. Дефект в проводке до клиента → `engine.call(...)`;
  дефект в конверте/транспорте → живой сервер через `tests/harness`.
- **Форма ответа живого харнесса** (`rpc.call_tool` → `{envelope, data, code, is_error, facts}`): `envelope` —
  ЦЕЛИКОМ JSON-RPC, поэтому структурированная часть лежит в `envelope["result"]["structuredContent"]`, а не
  в `envelope[...]`. Ошибка чтения этого уровня выглядит как «паритет сломан» на исправном сервере.
- **Наборы — самостоятельные скрипты, а не pytest-функции.** `python_files = ["test_suites.py"]`: pytest
  собирает ТОЛЬКО раннер, а он запускает `tests/**/test_*.py` подпроцессом и смотрит exit-код. Отсюда:
  `pytest.mark.xfail` внутри набора не работает вовсе (открытая находка оформляется своим маркером в выводе),
  маркеры (`live`, `sim`) навешивает раннер по имени файла/каталога, а новый файл попадает в гейт сам.

- **`ToolResult.data` при отказе равен `None` — читать его сразу после вызова нельзя.** `r.data[...]`
  после неуспешного вызова роняет НАБОР питоновским трейсом, и код отказа, который сервер честно
  вернул, в выводе не появляется вовсе: красное перестаёт объяснять причину. Правило: данные брать
  помощником вида `data_of(result, msg)` — на отказе он печатает `вместо успеха <КОД>: <сообщение>`
  проваленной проверкой. Образец: `tests/quick/test_montage_tools.py`.
- **Пропуск «с причиной» под ВНЕШНИЙ БИНАРЬ — слепая зона гейта, а не аккуратность.** Пропускать
  можно то, чего у раннера быть не может в принципе (веса моделей — гигабайты). Пакет менеджера
  пакетов (ffmpeg, LibreOffice) ставится в джобе, иначе половина набора в CI не исполняется, и
  зелёный цвет означает «не проверяли». Разрыв между ветками бывает кратным — замер по наборам
  монтажа показал, что без бинаря не исполняется больше половины. Проверка при заведении пропуска:
  прогнать набор ОБЕИМИ ветками
  (`PATH` с бинарём и без) и сравнить счётчики; расхождение — это то, чего гейт не видит.
- **Наборы — линейный скрипт: имя, объявленное НИЖЕ, ловится только исполнением.** Ни `ruff` (F821
  молчит: имя определено, просто позже), ни `mypy` этого не видят. А если блок лежит в ветке,
  которая на раннере пропускается, ошибка доживёт до первого локального прогона. Вставляя блок в
  набор, проверяй, что все его имена объявлены ВЫШЕ, и гоняй набор целиком, а не глазами.

- **Свойство сильнее примера — но «не падает» это самое слабое свойство.** Иерархия силы, снизу вверх:
  не бросает исключение → сохраняет тип → держит инвариант → идемпотентно (`f(f(x)) == f(x)`) → roundtrip
  (`decode(encode(x)) == x`). «Не упало» принимать как достаточное НЕЛЬЗЯ — это тестовая форма немого отказа.
  Где у нас просятся свойства: нормализаторы и санитайзеры путей (`safe_resolve`, `_norm`) — идемпотентность
  и инвариант containment; маппер `код → ErrorDetail` — сохранение класса реакции; сериализация
  `ToolResult → конверт MCP` — roundtrip по полям контракта. Упавшее свойство классифицируй, а не чини
  вслепую: баг кода / неверно сформулированное свойство / кривой генератор — три разных исхода.
- **Снял рукописный перечень — повесь на его место ТЕСТ-ИНВАРИАНТ, и в тот же прогон.** Перечень,
  обязанный совпадать с иерархией классов или с декларацией, разъезжается молча; заменив его на
  общий механизм, проверь свойство («каждое исключение зоны наследует базу», «каждый код из yaml
  есть в наборе») обходом `ast`/загрузкой файла, а не глазами. Такой тест окупается сразу, а не
  «когда-нибудь»: инвариант на исключения нашёл две зоны мимо базы в ПЕРВЫЙ прогон, одна из них —
  реальная брешь (битая декларация советов приезжала клиенту как `INTERNAL_ERROR`). Осознанное
  исключение из инварианта пиши В ТЕСТЕ с причиной, а не молчанием в списке.
- **Выживший мутант — четыре разных диагноза, и только один из них «дыра в тестах».** Прежде чем радоваться
  или чинить: (1) настоящая дыра → писать тест; (2) эквивалентный мутант (`+0`, `*1`, порядок независимых
  операций) → поведение не изменилось, тест ни при чём; (3) мутация попала в МЁРТВЫЙ код → удалять код,
  а не покрывать; (4) непокрываемая граница ввода-вывода → задокументировать, не имитировать. Без этой
  сортировки счётчик выживших превращается в шум. Если гоняешь мутации пачкой — ставь перед ними `mypy`:
  всё, что ловит типизация, из выживших исчезает, остаются настоящие пробелы.
- **Пятый диагноз, самый частый у нас: сценарий не ДОБИВАЕТ до механизма.** Мутация выжила не
  потому, что механизм не нужен, а потому, что тест до него не доходит. Эталон S24 (`M113`):
  вырезал компенсацию у `structure_reconcile` — набор остался зелёным. Разбор: сценарий подсовывал
  помеху ЕДИНСТВЕННОЙ сущности, она срабатывала ДО первого переноса, откатывать было нечего — и
  ассерт «каталог вернулся на место» проходил при вырезанном откате. **Правило: механизм отката,
  компенсации, повтора и «частичного результата» проверяется только падением на ВТОРОЙ операции** —
  первая обязана успеть сделать то, что придётся отменять. Сформулируй заранее, ЧТО именно должно
  быть отменено; если ответ «ничего», сценарий не про компенсацию.
- **Приёмочный вопрос к набору инструментов — не «все ли покрыты», а «сможет ли LLM без другого контекста
  решить задачу ТОЛЬКО этими инструментами».** Сценарий приёмки должен быть: независимым от предыдущих,
  только на чтение, с устойчивым ответом (не «сколько сейчас записей» — оно меняется), не решаемым одним
  keyword-поиском, требующим пагинации и склейки разных полей (id / имя / дата / путь). Такой набор ловит
  дыры, невидимые юнит-тесту: нечитаемое описание параметра, отсутствующий обратный индекс, ответ, из
  которого не следует следующий шаг.

## Анатомия теста: четыре вопроса, на которые отвечает КОД, а не проза

Тест обязан отвечать на четыре вопроса — **строением**, не комментарием. Проза в исходнике не
читается никем и расходится с реальностью первой же правкой; строение расходиться не умеет.

| Вопрос | Где живёт | Провал на ревью |
|---|---|---|
| **Что** тестируем | имя сценария + вызванный механизм | по имени не видно, что именно упадёт |
| **Зачем** | одна строка docstring (+ `D#`/`F#` для регрессии) | зачем не сформулирован = зона не выбрана |
| **Что проверяем** | наблюдение: поле контракта, код реакции, строка консоли | ассерт смотрит на внутренность, а не на наблюдаемое |
| **Какой результат ждём** | ожидание рядом с наблюдением, ФАКТ печатается при отказе | «ждали успех, получили провал» без кода и причины |

- **Состояния процесса в исходнике теста НЕТ.** Статус находки (`OPEN-CONFIRMED`, `⬜→🟢`,
  «обнови `CATALOG §E`»), история «прежде было X», планы, номера сессий, задачи — вон. Ссылка
  `D#`/`F#` допустима одним тегом в однострочном docstring: она **адресует эксплойт**, а не хранит
  статус. Статус живёт в реестре (`docs/roadmap/02_findings.md`, `CATALOG §E`) — у факта один
  хозяин; копия в тесте — второй источник правды, и он разъедется (правило «два источника одной
  правды работают ровно наполовину»).
- **Причина отказа ПАРСИТСЯ, а не предполагается.** При провале тест обязан достать из ответа
  фактический код (`ErrorDetail.code`), класс реакции и сообщение — и напечатать их против
  ожидаемого. `assert r.status == "success"` без вывода кода превращает отказ сервера в загадку и
  заставляет отлаживать заново то, что сервер уже честно сказал. Образец — `data_of(result, msg)`
  в `tests/quick/test_montage_tools.py`.
- **Ожидание объявляется НАМЕРЕНИЕМ, а не вычисляется из источника, который читает продукт.**
  Взять ожидаемый код из `config/server_reactions.yaml`, по которому сервер и отвечает, — значит
  получить тест, зелёный на сломанном сервере. Граница: из реестра берётся СЛОВАРЬ (такой код
  существует, его класс такой-то, шаблон сообщения такой-то), а КАКОЙ код ждём в этом сценарии —
  пишется в сценарии. Это не противоречит «эталон вычисляется, а не вписывается»: там вычисляется
  ОБЪЁМ (все дефолты доехали), здесь фиксируется ВЫБОР (ждём именно `PATH_ESCAPE`).
- **Повторная проверка — не надёжность, а стоимость.** Одно требование проверяется в одном месте:
  у зоны есть хозяин (`CATALOG §A–D`). Тот же ассерт в трёх наборах даёт три красных на один
  дефект и три правки на одно изменение требования.

## Живой сервер: что знать ДО первого прогона (иначе выясняется отладкой)

Проверено на своей шкуре в S24 — каждый пункт стоил ходов.

| Факт | Следствие для набора |
|---|---|
| **Файрвол банит сам прогон**: 60 запросов/мин, бан после 3 нарушений на 24 часа | Длинный сценарий с одного адреса получит `Blocked: IP заблокирован` — и это будет выглядеть как дефект продукта. Либо разносить фазы по процессам (как рой), либо поднимать порог через `MCP_CONFIG` (копия боевого конфига, отличие ровно в одном пороге — и тест обязан это доказывать) |
| **Клиентский таймаут харнесса — 30 с** | В CI набор идёт под `coverage` на слабом раннере: тяжёлый вызов (дерево с материализацией книг) выходит за предел и падает `httpx.ReadTimeout`. Поднимать `rpc.timeout` в наборе — это предел КЛИЕНТА, а не свойство сервера |
| **Область и реестр — общие на весь файл** | Сценарии разводить именами (ниша на сценарий) и фильтровать выдачу по префиксу пути. Глобальный ассерт «висящих нет» упадёт из-за соседнего сценария, где висящий заведён НАМЕРЕННО |
| **Новый файл `tests/**/test_*.py` попадает в гейт САМ** | Медленный или мигающий набор становится проблемой всех. Мерить время до коммита |
| **Env-двери сервера**: `MCP_WORKSPACE`, `MCP_CONFIG`, `MCP_AUTH_TOKEN`, `MCP_PORT`, `MCP_ALLOWED_HOSTS` | Через `live_server(env={...})`. Калитку `MCP_ALLOW_NO_AUTH` НЕ трогать: она снимает проверяемый слой (`F74`) |
| **Форма ответа**: `env["data"]`, `env["facts"]`, `env["code"]`, полный конверт — `env["envelope"]["result"]["structuredContent"]` | Уровнем выше `structuredContent` НЕТ. Сырой HTTP — `rpc.request(method, params, extra_headers={...})` (именно `extra_headers`) |

**Сторонний клиент, который не умеет наш ключ** (conformance и подобные) — прокси
`tests/harness/auth_proxy.py` добавляет заголовок, оставляя auth включённым. Прокси НИЧЕГО не
чинит: `Host` передаётся как есть, иначе он спрячет проверку, которую тест и должен показать.

**Пропуск в гейте — ложный зелёный.** Набор, зависящий от внешнего инструмента, пропускается
локально с причиной, но в своей CI-джобе обязан ПАДАТЬ при отсутствии инструмента
(`VPM_CONFORMANCE_REQUIRED=1`): иначе сломавшаяся установка даёт зелёную джобу, ничего не проверив.

## Студия (React/TS): что здесь вообще подлежит проверке

Фронтенд-кода в проекте пока нет ни одного файла — раздел вступает в силу с первого `.tsx`.
Конвенции выше НЕ меняются: тест — сценарий реального поведения, ассерт — на контракт, docstring
терсовый, эталон вычисляется, а не вписывается. Меняется список того, что обязано быть проверено.

**Четыре инварианта студии, которые обязаны стать тестами** — правило проекта «инвариант вешается
тестом, а не дисциплиной» (`20` §4а):

1. **Размер/шрифт мимо токена валит проверку.** Это временная замена храповику для UI: сторож
   `.tsx` не заведён (условие — первый компонент), значит инвариант держит тест.
2. **Каждый примитив отдаёт стабильный `data-component`** (`20` §4б) — иначе на вопрос «какой
   компонент это рисует» не ответить ни по DOM, ни по скриншоту.
3. **Жест даёт РОВНО ОДИН вызов записи, и по отпусканию** (`20` §3). Тест СЧИТАЕТ вызовы: поток
   правок во время движения мыши иначе виден только по нагрузке, то есть поздно.
4. **Чужая правка не затирается молча** (`20` §0 п. 8): версия прочитанной строки устарела → код
   реакции и перечитывание. Ассерт — на конкретный код, а не на «показалась ошибка».

**Уровень вызова выбирается так же, как на сервере — по тому, где живёт дефект.** Отрисовка
компонента в изоляции не увидит дефект проводки до сервера; «жест → один `table_set` → ответ» —
сквозной сценарий против ЖИВОГО сервера, а не против мока клиента. Мок — только истинно внешнее.

**Анти-паттерны, специфичные для UI:**
- **снимок вместо ассерта** — краснеет на любом легитимном изменении вёрстки и не утверждает
  ничего о требовании: это ошибка «эталон вписан руками», перенесённая в разметку;
- **проверка реализации** — что компонент дёрнул `useState`, что эффект отработал. Проверяется
  наблюдаемое: что увидел человек и что ушло на сервер;
- **зелено, потому что ничего не нашлось** — UI-версия пустого ассерта: элемент не найден, ассерт
  по пустому множеству проходит всегда. Сначала распечатай, что реально в DOM, потом ассертируй.

Раннер и состав node-джоб гейта не решены (`20` §4). Пока их нет, «гейт зелёный» означает шесть
джоб `ci.yml` по Python, и ни одна из них про студию не знает: говорить «проверено» про UI на этом
основании нельзя.

## Core Workflow (под проект)

1. **Scope** — что тестируем: новый код / регрессия на D# / edge / adversarial-сценарий. **Карта зрелости** (`references/capability-aware-testing.md` §1): собери живой `tools/list`, разложи по 4 колонкам (реализован / honest-stub / запланирован / не заявлен); цель = закрыть колонку для семейства, вкл. неразвитое. Дыра зрелости = находка.
2. **Strategy** — сверить с `testing_strategy.md`; выбрать набор в `tests/` (или новый).
3. **Write (pytest)** — `def test_…`, docstring ОДНОСТРОЧНЫЙ (5 вопросов продуманы, но живут в commit), ассерт на `ToolResult`/код реакции с печатью фактического кода. Моки провайдеров.
4. **Execute** — `pytest -q`. Упал: классифицировать (ассерт vs окружение/флак), чинить корень, перезапуск. Флак: искать порядок/async/состояние firewall.
   **«Гейт зелёный» = все джобы `ci.yml`, а не один pytest.** Проверять ИЗ `.venv` и по exit-коду каждой:
   `ruff check .` · `mypy` · `pytest` · `bandit -r core server.py -ll` · `pip-audit`. Пропуск любой = утверждение
   без основания (S24: `bandit` был красным на 8 issues, пока сессии писали «гейт зелёный»).
   **Исключение в конфиге инструмента — заявка, а не факт:** `exclude` в `[tool.mypy]` не действовал (mypy
   приходит в модуль по импортам, а не обходом каталога) и прятал 35 ошибок. Сними исключение и посмотри,
   что оно на самом деле закрывало.
   **Локально зелёное ≠ зелёное в CI.** Различия, которые кусали: версия Python (пин `python_version`
   заставлял разбирать стабы чужой библиотеки чужим синтаксисом), способ установки (CI ставит `-e ".[dev]"`,
   лок не участвует — пол по advisory нужен в манифесте), и артефакты вне git.
5. **Проверь независимость от того, чего в git нет.** Тест, читающий веса моделей/кэш/внешний файл, зелен
   только там, где они уже лежат: в CI такой набор недостижим (S24/F91 — падал `KeyError` на пустом каталоге).
   **Красный ПЕРВЫЙ прогон, зеленеющий на повторе, — холодный кэш, а не почининный дефект.** Ловушка
   двусторонняя: (1) не приписывай себе позеленение — прогони ещё раз и скажи прямо, что разница в
   прогретом кэше весов; (2) в CI кэш ВСЕГДА холодный, значит такой тест там красный, и «у меня
   зелено» ничего не значит. Отличать замером, а не рассуждением: два прогона подряд.
   Правило: нет артефакта → **пропуск с причиной** (`⚠ веса не поставлены — живой прогон пропущен`), не провал
   и не молчание. Эталон считать из источника истины (опись), а не «больше нуля»: на чистой машине пустой
   список — правильный ответ инструмента, а не его поломка. Проверять фикс прогоном БЕЗ артефакта
   (`mv vendor/models vendor/models.hidden`), а не рассуждением.
6. **Report** — покрытие (`pytest --cov=core --cov=tools`), явно отметить дыры; находки severity 🔴🟠🟡⚪; связать с `D#`.
7. **Record** — решение → факт в историю; регрессия-тест ← D#.

## Сторожа проверяют на ВРЕМЕННОМ каталоге, а не в репозитории

Проверка, которую нельзя прогнать, не создав файл-нарушитель внутри `tests/` или `config/`, делается
редко и доказывается «я запускал руками» — то есть не доказывается вовсе. Отсюда требование к самому
сторожу: **корень приходит параметром** (`check(root: Path = ROOT)`), а не зашит константой.

Тогда его тест строит крошечный фикстур во временном каталоге и проверяет ОБЕ стороны каждой
проверки: ловит нарушение и молчит на чистом входе. Ложные срабатывания, найденные при написании,
закрепляются фикстурами (параметры функций, `with ... as`, `except ... as`, имя в комментарии вместо
команды) — иначе они вернутся при первой же правке разбора. Образец: `scripts/guards/invariants.py` +
`tests/quick/test_invariants.py`.

## Машинерия проекта: когда что звать (иначе построенное простаивает)

Инструменты есть с S25, и первая же задача после их постройки прошла мимо них. Порядок обязателен:

| Момент | Команда | Что даёт |
|---|---|---|
| **ДО правки кода сервера** | `python3 scripts/guards/blast_radius.py --query <файл>[:строка]` | какие сценарии держат это место. Ответ «ни одного» = правка невидима тестам: сначала сценарий |
| **Правка уже в дереве** | `python3 scripts/guards/blast_radius.py --affected` | ровно задетые сценарии + готовая точечная команда (секунды вместо полной матрицы) |
| **Точечный прогон** | `VPM_SCENARIO='a,b' python3 tests/scenarios/test_scenarios.py` | отбор по нескольким именам через запятую |
| **Осознанно меняешь поведение** | `python3 scripts/guards/what_if.py --intent intent.yaml` | три колонки: заявленное сбылось · **изменилось незаявленное** · заявленное не сбылось. Вторая колонка — скрытый риск |
| **Задет поток к клиенту** | маршрут в `tests/routes/routes.yaml` + `python3 tests/routes/test_routes.py` | доезжает ли значение (код, класс, рецепт, провенанс, факты) до клиента |
| **Рубеж «существует» ≠ «исполняется»** | `python3 scripts/guards/blast_radius.py --check-routes` | рубеж маршрута обязан исполняться его опорой |
| **Несколько состояний и порядков** | карта `tests/scenarios/*.map.yaml` | пути порождаются: новый переход = новые сценарии без кода |

**Куда что кладётся:** сценарий → `tests/scenarios/<тема>.yaml` · карта → `tests/scenarios/<тема>.map.yaml`
· шаг-помощник (то, чего вызовом не выразить) → `tests/scenarios/steps.py` · маршрут потока →
`tests/routes/routes.yaml`. Новый набор-скрипт заводить НЕ нужно: поведение описывается объявлением.

**Карта радиуса собирается медленно и вручную** (`--build`, сервер под покрытием, один сценарий = один
сервер). Устарела после больших правок — пересобрать; в гейт она не входит намеренно.

**Выходной гейт это проверяет механически:** тронут `core/`/`tools/`/`server.py`, а прогона сценариев в
ходе не было — Stop-хук блокирует со ссылкой на `--affected` (`vpm-delivery-gate.py`, проверка C).

## Сценарий как декларация (движок — этап `T11` в `docs/roadmap/14_testing_system_plan.md`)

Повторяющаяся часть теста — «поднять область, позвать инструмент, сверить контракт» — одинакова в
сотнях мест; различаются только условия и ожидания. Их место — в объявлении, а исполнение — общее:

```
given:  область/конфиг/env/предшествующие вызовы
when:   инструмент + параметры (последовательность)
then:   наблюдения — status · код реакции · класс · поля facts · строка консоли
why:    одна строка: какое требование это утверждает
```

Три правила, без которых объявление вредит:

1. **Сначала исполнитель, потом декларация.** В этом репозитории уже лежала `tests/config/scenarios.yaml`,
   ссылавшаяся на несуществующий `tests/runner.py`, и была удалена как мёртвая (`T3`). Декларация без
   раннера — не тест, а обещание, и она красит гейт в зелёный самим фактом существования.
2. **Ожидание объявляется, словарь берётся из реестра** (см. «Анатомия теста»). Иначе тавтология.
3. **Незакрываемое объявлением остаётся кодом.** Сценарий описывает условие и ожидание; хитрая
   подготовка (гонка, второй вызов, падающий посередине, мутация файла на диске) пишется на Python и
   зовётся сценарием как шаг. Попытка выразить в YAML всё подряд даёт язык программирования в YAML.

**Что язык УЖЕ умеет — проверь, прежде чем писать питонный набор.** Граница декларативного слоя —
это язык, а не клиент: харнесс умел подменять ключ и заголовки задолго до того, как сценарий научился
это объявлять, и из-за этого весь периметр держался на питоне без причины.

| Нужно проверить | Чем объявляется |
|---|---|
| вызов инструмента | `call:` + `with:` |
| метод протокола (`tools/list`, неизвестный метод) | `rpc:` |
| периметр: чужой `Origin`/`Host`, пустой или неверный ключ | `headers:` / `token:` на шаге |
| код HTTP (401/415 — он не в теле) | `http:` в ожидании |
| поведение РЯДА вызовов (частота, устойчивость) | `repeat: N` → сводка в `data._repeat` |
| один вызов ведёт в РАЗНЫЕ состояния | `router:` в переходе карты (`by` + `table`) |
| порядок вызовов как источник поведения | `walk.coverage: pairs` |
| известная дыра: ждём желаемого, сегодня его нет | `open: F###` |
| сложная подготовка | `python:` шагом в `steps.py` |

**Дополняй карту и сценарии по ходу работы — это не факультатив, а условие видимости.** Карта
молчит обо всём, чего в неё не положили, и три механизма делают это молчание громким:

- `blast_radius --blind` — ФУНКЦИИ сервера вне всех сценариев; храповик вниз, проверка `D` гейта поставки
  срабатывает по ФАЙЛАМ правки (`git diff` + сегодняшние коммиты), а не по слову в переписке. Ключ —
  имя функции, а не строка: строка сдвигается от любой правки, и построчная улика живёт до первого
  касания файла. Код 2 значит «улики нет» (карта не собрана) и НЕ равен «стало хуже».
- `router.covers` — таблица роутера сверяется с объявленным перечнем; непокрытое значение обязано
  быть названо в `skip` с причиной. **Это и есть разница между роутером и `if`:** таблица обязана
  быть пройдена целиком, ветка `if` — нет, и о забытой ветке никто не узнает.
- `suites_off_catalog` — новый питонный набор без зоны в `CATALOG.md` красит гейт: сначала спроси,
  почему это не выражается декларацией.

**Журнал прогона обязателен** для сценарного и живого слоя: запрос → ответ → код → строки консоли,
машиночитаемо, один файл на прогон. Без него «упало в CI, локально зелено» разбирается пересказом.

## Форму ответа НЕ угадывают — её читают или спрашивают у сервера

За одну сессию сервер поправил семь угаданных объявлений: `type: dir` вместо `directory`, `path`
вместо `name`, `scope: declared` вне перечня, отсутствующий `template_id`, канал под нишей мимо
таксономии, `{op: …}` вместо `{action: …}`, `RPC_-32000` вместо `-32002`. Каждая ошибка нашлась на
ПЕРВОМ прогоне и с точной причиной — это и есть довод за декларацию против питонного набора.

- **Закрепляй ФАКТИЧЕСКОЕ значение, а не догадку.** Прогон печатает «пришло X» — X и есть ответ.
- **Форму смотри у хендлера** (`Fact(type=…)`, `data=…`) или в `tools_inventory.golden.json`, либо
  подними её из журнала прогона (`tests/.journal/*.jsonl` пишет `data` каждого шага).
- **Сервер сказал «нельзя» — сперва проверь, не прав ли он.** `table_append` НЕ пишет сразу, а кладёт
  в очередь; мой первый сценарий утверждал обратное. Переписанный на настоящий контракт он стал
  сильнее исходного.

## Карту не пишут с нуля, если есть запись

Последовательность вызовов повышается до карты решёткой: `python3 scripts/guards/reproduce.py
--promote`. Состояния — ИДЕАЛЫ порядка (какие предметы уже видны снаружи), переходы — добавление
одного предмета. Смысл именно в решётке: линейная карта прошла бы записанным путём и не показала
ничего, а решётка даёт порядки, которых в записи НЕ БЫЛО, — их и проверяет обход.

Три правила, без которых порождённая карта будет вымыслом:

- **Предикат спрашивает КАЖДЫЙ предмет** — и тот, что уже есть, и тот, которого ещё нет. Иначе
  состояния различались бы длиной списка, а не наблюдением, и предмет, появившийся не в свой черёд,
  остался бы невидимым.
- **Чем наблюдают факт — объявляется** (`tests/harness/observations.yaml`: адрес имени, чтение,
  ответ при наличии и при отсутствии). Необъявленный факт останавливает работу с ИМЕНЕМ
  недостающего: тихо пропустить значит выдать неполную карту за полную.
- **Судит порождённое разбор ХАРНЕССА** (`analyse` + `load_map`), а не второй судья в генераторе.
  Он же ловит вымысел до всякого сервера: на первой пробе так нашлась склейка имён, из-за которой
  пустое состояние и состояние с первым предметом оказались одним.

Зависимость сужает решётку: если имя раннего предмета названо в аргументах позднего, порядок
фиксируется. Проверка КОНСЕРВАТИВНА намеренно — лишняя зависимость только сузит перебор, пропущенная
породит порядок, невозможный на живом сервере, и обход упадёт не там, где интересно.

## Улику якорят к ПРОГОНУ, а не к часам

Тест, наблюдающий файл (след сервера, журнал, отчёт), обязан принимать только запись СВОЕГО прогона.
Окно «за последние N секунд» кажется достаточным и не является им: файлы переживают прогон, и на
замере выключенный механизм зеленел на строке предыдущего запуска — мутация выжила 8 проверок из 8.
Якорь — отметка старта наблюдаемого процесса (`LiveServer.started`), а не системное время.

То же в обратную сторону: если наблюдаемое пишет ТОЛЬКО ваш прогон, докажи это выключением
механизма — сценарий обязан покраснеть. Не покраснел — тест не добивает до механизма.

Готовое: след вызовов сервера читается шагом `trail_says` (`tests/scenarios/steps.py`), сценарии —
`tests/scenarios/observability.yaml`. Инструмента, читающего след, нет и заводить его незачем:
сценарий судит снаружи.

## Простой тест или симуляция: чем они РАЗНЫЕ и что каждый не ловит

Правило и его условия — канон `docs/roadmap/08_pass_closure.md` §C (ступень C1/C2). Здесь только
то, что нужно при ВЫБОРЕ формы; копии канона тут нет намеренно.

| | простой тест (C1) | симуляция (C2) |
|---|---|---|
| что доказывает | ПРИЧИНУ на уровне кода и контракта | ЭФФЕКТ на живом сервере |
| как ходит | зовёт функции и слои напрямую | реальными инструментами через транспорт |
| сценарий | набор логики, пусть с условиями и состояниями | сложный, с хитростями против ожидаемого пути |
| видит ли молчание | нет | да, консоль читается, и МОЛЧАНИЕ судится наравне с ответом |
| чего не ловит | всё, что живёт только в бою | всё, чья причина не воспроизведена кодом |

Выбор не вкусовой: **C1 без C2 — теория без реальности, C2 без C1 — эффект без доказанной
причины**, и проход закрывается только обоими.

**Третий предмет, которого нет ни у одного из двух: обход правила САМИМ ИИ.** Оба нацелены на
сервер. Дисциплину ловит только симуляция, чей предмет — путь ИИ, и топорный сценарий здесь
бесполезен: он проверяет ожидаемый ход, а обход живёт на неожиданном. Такой сценарий обязан
сравнивать поведение с ОБЪЯВЛЕННЫМ правилом, иначе подтверждает привычку, а не дисциплину.
Отсюда же: цикл до кода обязан покрывать тесты и скрипты, а не только `core/` — правило, живущее
в хуке или стороже, ломается их правкой. Остаток `175b`.

## Проверка пишется по КЛАССУ нарушения, а не по замеченному примеру

Директива владельца 2026-09-06: «копировать такие штуки дословно нельзя — это ненадёжно и рухнет
при первой же реальной проверке с отклонением. Проверки надо писать так, чтобы они закрывали любые
возможные варианты и комбинации, при этом краткой но надёжной формулой».

Пример цены, оплаченный в тот же день. Проверка «кириллица в оболочке», написанная по двум
случившимся примерам (`$ДОМ`, `К=1`), пропускала **семь вариантов из восьми**: другой алфавит
(украинская `і`, греческий), присваивание не в начале строки, после `&&`, в подоболочке, через
`export`, имя из ASCII с одной чужой буквой (`klon_дом=`), слова `unset`/`for`, забирающие имя без
знака `=`. Написанная по классу — «не-ASCII там, где оболочка ждёт ИМЯ», три позиции, алфавит не
перечисляется — та же формула держит все 19 проб, включая 7 законных, которые обязана пропустить.

**Как писать:**

1. Назови КЛАСС одной фразой: что именно незаконно и почему («чужая буква в позиции имени»,
   а не «доллар и русские буквы»).
2. Перечисли ПОЗИЦИИ и роли, а не значения. Алфавиты, имена и пути — переменная часть класса.
3. Проверь обе стороны на КОМБИНАЦИЯХ: каждая позиция × каждое отклонение. Один пример на класс —
   это не проверка, а иллюстрация.
4. Законное держи в той же пробе явным списком: формула, поймавшая законное, будет выключена
   в первый же день, и класс останется без сторожа вовсе.

Признак, что проверка написана по примеру: в ней перечислены конкретные строки, которые ты видел
в выводе. Признак, что по классу: перечислены позиции, а примеры живут только в пробе.

### Судим СОСТОЯНИЕМ, а не стартом

Директива владельца 2026-09-06: «судить надо не стартом, а состоянием — это касается всего: если
задача стартовала, но тихо упала или громко, мы об этом не узнаем, потому что не проверяем».

**Класс.** Механизм объявляется живым по СОБЫТИЮ («запустился», «подключился», «ответил один раз»),
а дальше состояние либо не пересчитывается, либо пересчитывается по ЧУЖОМУ отчёту. Оба варианта —
одно и то же: живым считается тот, о чьей смерти нам не сообщили.

**Формула проверки.** У каждого долгоживущего механизма состояние обязано выводиться из
НЕЗАВИСИМОГО наблюдения, а не из сообщения о старте и не только из чужого лога:

| что судим | негодная улика | годная улика |
|---|---|---|
| туннель | строка «Registered tunnel connection» в логе | живые сокеты к краю + ответ публичного URL |
| фоновая задача | «процесс запущен» | код возврата ИЛИ признак результата на диске |
| сервер | «поднялся на порту» | ответ на запрос, а не факт `bind` |
| хук | «объявлен в settings» | отметка в следе за окно свежести |
| сторож | «файл на месте» | вердикт прогона свежее правки |

**Три вопроса к любому «работает»:** чем это наблюдается НЕЗАВИСИМО от самого механизма · что
показывает наблюдение, когда механизм умер молча · через сколько времени мы об этом узнаем.
Нет ответа на все три — состояние не судится, судится старт.

Цена класса измерена 2026-09-06: туннель показывал «поднят», семь его сокетов к краю висели в
`CLOSE-WAIT`, коннектор получал `HTTP 530`, и владелец полсессии искал причину в протоколе адреса.

### У УЛИКИ тоже есть класс, и это не фигура речи

Мы говорим «улика» постоянно, но улика — не одна вещь: у неё есть РОД (что именно доказано) и
ОБЛАСТЬ (на что это распространяется). Пока род не назван, улика доказывает ровно один случай, и
проверка неизбежно пишется по примеру. Названный род почти всегда даёт одну формулу на целый
класс — короче в записи и надёжнее в обслуживании, потому что новый вариант попадает под неё сам.

Три случая одного дня, каждый оплачен отдельно, и все три — один невыделенный класс:

| улика по примеру | какой класс за ней стоял | цена промаха |
|---|---|---|
| `$ДОМ` и `К=1` не подставились | не-ASCII в позиции ИМЕНИ оболочки | 7 вариантов из 8 проходили |
| `<<'EOF'` в конце строки снимался | ДАННЫЕ в команде: тело heredoc и аргумент `-c` | два ложных отказа на законной работе |
| `.txt` не попадал в набор судей | новорождённый файл ЛЮБОГО рода | три промаха за сессию |

**Как этим пользоваться:** получив улику, спроси не «что она доказала», а «род чего это». Ответ
и есть формула. Если род назвать не удаётся — улика пока единичная, и её место в пробе как
пример, а не в правиле как определение.


## Мутация: сперва докажи, что она ЛЕГЛА

Мутация, не попавшая в файл, даёт зелёный прогон и ложный вывод «тест не ловит». Порядок: якорь
текстом → `git diff --stat` → прогон → восстановление → `git status` пуст. Дополнительно:

- **Починка дефекта КРАСИТ набор, который утверждал старое поведение** — это сигнал, а не поломка:
  набор кодировал ровно тот дефект, который чинят. Перед сменой контракта грепни, кто его утверждает,
  и правь утверждение вместе с кодом — иначе красный придёт из полного прогона и будет выглядеть
  регрессией.
- **Прогон, ничего не отобравший, — не зелёный.** Опечатка в `VPM_SCENARIO` давала «0/0 · ВСЁ
  ЗЕЛЁНОЕ»; теперь каждое имя отбора обязано совпасть.
- **Параллельно наборы не гонять** — не только из-за видеокарты: файрвол считает частоту по IP, и
  второй прогон даёт ложные отказы в `bot_army`/`rate_limit`.

def test_fs_read_blocks_path_traversal():

    # (5 вопросов продуманы — рацио в commit/history, не в docstring)

## Наборы делят одну видеокарту — параллельно не гонять

Живые наборы (`test_providers`, `test_structure` с медиа) поднимают локальные модели на карте.
Два прогона разом дают `CUDA out of memory` в том наборе, который просто оказался вторым, —
и это выглядит как дефект кода, которого нет. Замер S24: фоновый `pytest -q` и одиночный
`test_providers.py` в одном ходе → OOM на 15.98 ГБ при 7.71 ГБ, уже занятых первым процессом.

Правило: прогон набора и полный `pytest` — по очереди, а не одновременно. Красный тест после
параллельного запуска сначала проверяется на гонку за железо (`ps` + занятость VRAM), и только
потом ищется в коде.

## Constraints

### MUST DO
- Читать `testing_strategy.md` + историю до тестов; продумать 5 вопросов, но docstring держать ОДНОСТРОЧНЫМ (рацио — в commit/`history`, не в коде).
- Тестировать happy + error/edge + adversarial; регрессия на каждый закрытый D#.
- Покрывать НЕразвитые возможности: honest-stub обязан падать честным кодом реакции (не фейковый `success`), для запланированного — `xfail(strict=True)`-spec с причиной-ссылкой на ledger.
- Ассертить контракт `ToolResult`/`ErrorDetail`/код реакции, не truthy.
- Размещать по структуре: быстрый→`tests/quick/` (удалить после), постоянный→`tests/<name>/`+`history.md`. Поведенческий тест — против ЖИВОГО сервера (JSON-RPC на `/mcp`). Мок только внешних провайдеров; сбрасывать состояние firewall.
- Прогонять `pytest` + coverage, явно отмечать дыры; перед словами «гейт зелёный» — ВСЕ джобы `ci.yml` по exit-коду.
- Принимать регрессию только мутацией: сломать фикс (`if False and …`) → тест обязан покраснеть → вернуть
  фикс ОБРАТНОЙ заменой (не `git checkout` — снесёт соседние правки) → строка `M#` в `tests/CATALOG.md §F`.
  Патчить якорем с проверкой (`assert old in s`) — молча не совпавшая замена даёт «мутация не поймана»,
  то есть ложный вывод о качестве теста. Записывать, СКОЛЬКО ассертов покраснело: одна мутация, красящая
  ассерты в соседней секции, — сигнал, что зоны пересекаются, а не повод радоваться.
- Держать тест независимым от того, чего нет в git: нет артефакта → пропуск с причиной, не провал.
- Связывать находки с `D#`, писать решение→факт в историю.
- Печатать при провале ФАКТИЧЕСКИЙ код отказа и причину из ответа — не только «ожидал успех».
- Проверять требование в ОДНОМ месте: у зоны есть хозяин (`CATALOG §A–D`), дубль-ассерт — удалять.

### MUST NOT
- Звать реальные API провайдеров (litellm/stable-ts) в юнит-тестах.
- Тесты, зависящие от порядка / общего состояния.
- Игнорировать флак (карантин + чинить, не «прогнать до зелёного»).
- Тестировать детали реализации вместо поведения.
- Приносить Jest/k6/Playwright-практики.
- **Клепать простые тесты и класть их куда попало** (вне `tests/` по структуре), оставлять быстрые «на потом».
- Mock-only тест вместо сценария против реального сервера, когда проверяется поведение сервера.
- **Держать в исходнике теста состояние процесса**: статус находки, напоминание реестру,
  историю «прежде было X», планы, номер сессии. Хозяин статуса — реестр, не тест.
- Вычислять ожидаемый код отказа из того же конфига, по которому отвечает сервер (тавтология).
