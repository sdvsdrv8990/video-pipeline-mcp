# Engineering Questions — video_pipeline_mcp

«Думай, прежде чем писать». Скилл — **не исполнитель**, а структурированный опросник: по типу задачи выдаёт вопросы, на которые ИИ обязан **ответить письменно** до и во время работы, после чего передаёт domain-скиллу. Опирается на канон `the project workflow (memory project-workflow-canonical)` (5 вопросов, 4 уровня, 5 типов задач) и **углубляет** его — не дублирует.

Правило: сначала ответы на вопросы → потом код. Ответы на ключевые вопросы уходят в commit + `docs/roadmap/_sessions.md` (решение→факт) и commit-сообщение — **НЕ** многострочным блоком в код/docstring (владелец 2026-07-05: process-нарратив в коде = зараза).

---

## Как пользоваться

1. **Классифицируй задачу** (тип задачи: новый код / баг-фикс / рефакторинг / новый функционал / тестирование; + наши: новый инструмент, security-аудит, правка конфига).
2. **Прогони общий блок** (ниже) + **специфический блок** по типу (`references/question-bank.md`).
3. **Ответь письменно** — коротко, по делу; неотвеченный красный вопрос = стоп, не кодим.
4. **Передай** результат domain-скиллу по связке ниже, зафиксируй ответы (commit/история).

Не превращай в ритуал: на мелочь — общий блок; на существенное/рискованное — полный.

## Связки: какие скилы стакать по типу задачи

Единственный источник этой таблицы — здесь (глобальный `CLAUDE.md` ссылается сюда, а не дублирует).
Это **не роутер по ключевым словам**: нативный выбор скила по `description` работает сам, а таблица
отвечает на другой вопрос — что подключить ЕЩЁ и в каком порядке, когда задача многогранная.

| Тип задачи | Связка (по порядку) |
|---|---|
| Новый инструмент / функционал | `project-conventions` (куда/как назвать) → `mcp-developer` (сборка) → `anti-hardcode` (не зашить значения) → `test-master` (тесты, включая честный стаб) → `security-reviewer` (если пишет/удаляет/отдаёт наружу) |
| Баг-фикс | **`systematic-debugging` (корневая причина ДО правки — обязателен)** → domain-скилл по файлу (`mcp-developer`/`security-reviewer`/`reactions-errors`) → `test-master` (регрессия, которая КРАСНЕЛА до фикса) |
| Рефакторинг / чистка | `code-quality` (выбрать ось; ось 1a — «механизм из библиотеки, наш слой политика») → `anti-hardcode` (если значения/ветки) → `test-master` (зелёное до и после) |
| Правка существующих файлов, батч/скриптом | `verified-edits` (якорь из свежего чтения, пост-условие на каждый файл) + domain-скилл |
| Security-аудит | `security-reviewer` (сначала выбрать направление: входящее/исходящее) → `test-master` (регрессия на каждую находку) |
| Тесты | `test-master` → `project-conventions` (размещение) |
| **Правка кода сервера (`core/`, `tools/`, `server.py`)** | `blast_radius --query` (что держит это место — ДО правки) → domain-скилл → `test-master` (сценарий, а не новый скрипт) → `blast_radius --affected` + точечный прогон → `what_if` (если поведение меняется осознанно) |
| **Задет поток данных к клиенту** (код отказа, класс, рецепт, провенанс, факты) | `test-master` §маршруты → маршрут в `tests/routes/routes.yaml` → `test_routes.py` → `blast_radius --check-routes` |
| Разобраться в незнакомом месте, «где это лежит / кто это читает» | `code-navigation` (точка входа + проверка запуском) → domain-скилл |
| Красный тест / выживший мутант / «локально зелено, в CI нет» | `systematic-debugging` (улики по рубежам слоёв) → `test-master` |
| **Наблюдаемость, аудит-след, бюджеты (`DIM-7`/`DIM-11`, I5)** | `observability` (что мерить и что делать, когда число стало плохим) → `reactions-errors` (чем отказ доедет до клиента) → `test-master` (сценарий против живого сервера, а не чтение кода) |
| Правка конфига | `anti-hardcode` (D2: декларация действительно читается?) → `security-reviewer` (если видна клиенту) |
| Зависимости: добавить/поднять/CVE | `dependency-hygiene` (манифест↔лок↔`.venv`, чужой индекс, пин) → `verified-edits` (эффект правки манифеста виден не там, где правка) → `test-master` (гейт ИЗ `.venv`) |
| Реакции/ошибки | `reactions-errors` → `test-master` (код реакции в ассертах) |
| Скилы/хуки/процесс | `skill-curator` (улучшать существующий, новый — только при смене границы) |
| Фронтенд: новый экран/компонент | `frontend-design` (замысел: токены, отказ от штампов ИИ) → `project-conventions` (размещение) → `no-unnecessary-effects` (дерево решений ДО `useEffect`) → `verified-edits` §3а |
| Фронтенд: правка существующего компонента | **`verified-edits` §3а первым** — правка UI задевает соседнее чаще прочего (снесённая анимация, тронутые иконки); доказывать разбором, а не глазами → `code-navigation` (какой компонент рисует это место) → `no-unnecessary-effects` (если трогаешь состояние) |
| Фронтенд: экран показывает данные из `workspace/` или пишет на сервер | `security-reviewer` (раздел «Студия»: провенанс данных в разметке, дверь записи одна) → `test-master` (инвариант тестом) |
| «Одно и то же в пяти местах»: карточки, кнопки, отступы | `code-quality` (это `F99`/`F100` в UI — пять источников одной правды) → `anti-hardcode` (размер/шрифт мимо токена) → `test-master` (инвариант вешается тестом, а не дисциплиной) |
| Гейт красный / «гейт зелёный» под вопросом | `systematic-debugging` → `test-master` (все шесть джоб `ci.yml` по exit-коду, не один pytest) → `dependency-hygiene` (advisory, манифест↔лок↔`.venv`) → `verified-edits` |
| Документ спорит с диском, статус не сходится, снятое воскресает | `docs-governance` (роли, один хозяин факта, зона снятого) → `verified-edits` (утверждение проверяется запуском) |
| Окно контекста кончается, ставим ещё один MCP/скилл/хук | `context-budget` (замер: MCP дорог, скилы дёшевы) → `skill-curator` (если резать описания) |
| Сверка планов с диском, снятие устаревших статусов | `project-conventions` (где что лежит — «Карта системы») → `verified-edits` (якорь из свежего чтения) → `test-master` (утверждение проверяется ЗАПУСКОМ, не соседним документом) |

**Метод для больших сплошных задач (проверен S24).** Разведка — несколькими агентами параллельно и
ТОЛЬКО на чтение; правки и коммиты — последовательно, один шаг = один смысл = один коммит. Параллельные
правки в одно дерево дают потерянные правки, а не скорость. Отчёты разведчиков писать файлами на диск:
иначе результат не переживает обрыв сессии. Три категории находок, и третья важнее первых двух:
заявлено сделанным — а нет; заявлено открытым — а закрыто; **сделано, но нигде не записано**.

Правило перед вызовом: **скилл должен существовать** — сверься со списком в системном сообщении
или `ls ~/.claude/skills/`. Имя из памяти = самый частый способ позвать несуществующее.
Стакай минимум: на однострочник вся связка не нужна.

## Общий блок (любая задача) — канон памяти `project-workflow-canonical`

**5 вопросов перед работой:**
1. Что читаю (git-историю файла + `docs/roadmap/02_findings.md`)?
2. Что вижу — какие решения/ошибки/`D#`/`G#` уже приняты здесь?
3. Что меняется?
4. Что учту — какие прошлые ошибки НЕ повторю (не переоткрыть закрытый `D#`, не сломать проводку)?
5. Что запишу (решение→факт, куда)?

**4 уровня анализа:** код → поведение (наблюдаемое) → поток данных (куда течёт/утечёт) → долгосрочный (через 6 мес).

Дальше — **специфический блок по типу** (`references/question-bank.md`): там глубокие вопросы про контракты, ОБА направления безопасности, хардкод, размещение, тесты, регрессии.

## Мини-срез специфических блоков (полностью — в `references/question-bank.md`)

- **Новый инструмент/функционал:** какой Bounded Context? контракт `ToolResult`? логика в `core/`, а обёртка тонкая? антидубль? новые коды/факты в реестры (D4/D25)? он **выводит** данные клиенту (→ outbound-security T1/T5)?
- **Баг-фикс:** воспроизведён эмпирически? корневая причина, не симптом? это уже известный `D#`? регресс-тест, который падал ДО фикса?
- **Рефакторинг:** поведение точно не меняется? тесты зелёные ДО и после? какую ось `code-quality` закрываю? не тяну ли логику в обёртку?
- **Security-аудит:** направление inbound или outbound? находка доказана запуском? проводка правила / загрузка конфига / fail-open проверены? не переоткрываю `D#`?
- **Тесты:** сценарий реального поведения, не проверка кода? против живого сервера? зрелость возможности (реализован / honest-stub / запланирован)? ожидание объявлено намерением, а не вычислено из конфига, который читает сервер? при провале печатается фактический код отказа?
- **Фронтенд-экран (`.tsx`):** какой этаж — примитив/экран/доступ к серверу? это пятый похожий компонент или вариант? размеры из токена? данные `workspace/` уезжают в разметку? запись одним вызовом по отпусканию? (полный блок G — `references/question-bank.md`)
- **Правка конфига:** значение реально **грузится** (анти-D2)? не оживляю мёртвый knob? hot-reload затрагивает контракт, видимый клиенту (rug-pull T3)?

## Приём замечания (владельца или ревью) — до того, как бросаться исполнять

Замечание — техническое утверждение, а не сигнал согласиться. Порядок:
прочитать целиком → **пересказать своими словами** → сверить с кодом (утверждение верно ДЛЯ ЭТОЙ
базы?) → оценить последствия → ответить технически → исполнять по одному пункту с проверкой каждого.

- **Непонятен хоть один пункт — не исполняй НИ ОДНОГО.** Пункты связаны; частичное понимание даёт
  правку, которую потом откатывать. Спроси по непонятным, назвав понятые.
- **Никакого «вы абсолютно правы» и «отличное замечание».** Это шум вместо содержания. Вместо —
  пересказ требования, уточняющий вопрос, либо сразу работа.
- **Замечание может быть неверным для нашей базы.** Возражай с техническим обоснованием
  (у нас так уже пробовали и записали `D#`; у нас нет SQL/веб-UI/мультитенантности), а не
  исполняй молча. Не можешь проверить — скажи, чего не хватает для проверки.
- **Владелец подтвердил решение — оно принято.** Дальше исполняем полностью, а не спорим второй раз.
