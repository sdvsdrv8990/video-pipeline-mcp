# Оси качества — детальный чек с примерами проекта

> Разворачивает 8 осей из `SKILL.md`. Для каждой: как искать (grep/чтение), эталон, анти-паттерн из аудита проекта.

---

## 1. Архитектура-адеренс (🔴 первая)

**Инвариант:** обёртка тонкая → логика в `core/` → `ToolResult` наружу → код `server_reactions`. Слоя `config/ops/` в проекте нет (снят S22, каталог снесён по `F83`).

**Как искать толстую обёртку:**
- В теле инструмента (`server.py`, `tools/`) — бизнес-ветвления, циклы обработки, знание формата данных, которых нет в декларации. Признак: обёртку нельзя переиспользовать для соседней операции, потому что логика зашита.
- Реальность проекта: часть инструментов сознательно inline (таблицы, structure_*), т.к. слоя `config/ops` нет вовсе, а `core/engine` — generic реестр+диспетчер. Это **задокументированное** отклонение (как G16-путь). Дефект качества — только **недокументированный** толстый обёрточный код или дубль логики, который просился в декларацию/`core`.

**Эталон:** логика в `core/engine/*.py` / `core/*`, обёртка валидирует вход и зовёт ядро.

## 1a. Механизм — библиотечный, наш слой — политика (🔴)

**Инвариант:** мы решаем, ЧТО выбрать и почему; КАК это сделать — знает библиотека. Свой код появляется там, где у библиотеки механизма нет, и это проверено вызовом, а не памятью.

**Как искать:**
- `grep -n "if .*==" ` вокруг вызовов чужого API — ветка под частный случай почти всегда означает непрочитанную сигнатуру.
- Перед своей реализацией: `inspect.signature(<чужая функция>)`, `[m for m in dir(obj) if …]`, дока версии, которая СТОИТ (не последней в интернете).
- Симптом: наш словарь «имя → поведение» повторяет то, что у библиотеки уже параметр.

**Эталон (S23, провайдеры):** `local.gpu.load_from_row` — объявленная карта «столбец строки → параметр `from_pretrained`». Новый рычаг библиотеки = строка в YAML. Свойства скачанного (`variant`) — в описи, не в строке и не в коде. Решение «целиком или с выгрузкой» — наша политика (`hardware.placement`), сам перенос — метод пайплайна.

**Анти-паттерн:** «поддержим fp16» отдельной веткой, когда `variant` — просто параметр; своя оценка памяти там, где у `accelerate` есть готовая (но: проверь применимость — для diffusers она не работает, и это выяснено запуском).

**Приёмка:** после правки строк меньше, функций столько же или больше. Рост строк требует объяснения: что именно библиотека не умеет и как это проверено.

## 2. Контракт на выходе + parity-gap (🔴, G14/D30)

**Инвариант:** всегда `ToolResult(status, data?, error?, facts?)`; ошибка — `ErrorDetail` внутри, никогда `raise` наружу или сырой текст.

**Parity-gap (G14/D30) — тонкое:** внутренний `ToolResult` богаче, чем MCP `CallToolResult`, который реально уходит клиенту. Проверь сериализацию на границе транспорта (`core/transport`): не теряются ли `facts`/`status`/структура, не уходит ли `error`/`facts` **вне** MCP `content` (D30 — клиент их не увидит). Богатый внутренний контракт, который клиент не получает — это разрыв качества.

**Как искать:** сравни поля `ToolResult` (`core/contracts/tool_result.py`) с тем, что кладётся в ответ в транспорте. Всё ли доезжает?

## 3. Честность незавершённого (🟠, G16)

**Инвариант:** заявленная, но не готовая возможность **кричит**.
- ✅ `raise NotImplementedError(...)` или `ToolResult(status="error", error=ErrorDetail(code="LOCAL_INFERENCE_FAILED"/"PROVIDER_FAILED"...))`.
- ❌ `return ToolResult(status="success", data={})` для нереализованного; ❌ `return None`/пустой список молча; ❌ docstring/история говорит «сделано», а функция — заглушка (doc-lie D3/D24).

**Эталоны честности в коде:** провайдеры (`core/providers/*`) с `NotImplementedError`; `TaskStatus` honest stubs. **Анти-эталон:** метод, у которого вызовов ноль (тихая дыра), и документ, заявляющий закрытым то, что открыто. Оба проверяются прогоном, а не чтением: `grep` вызывающих, сверка утверждения с диском.

**Как искать:** `grep -rn "TODO\|FIXME\|pass$\|return None\|NotImplementedError"` + сверка: то, что помечено готовым в истории, реально исполняет контракт?

## 4. Мёртвое (🟠, D28)

- **Dead inject-param:** параметр конструктора/функции принимается, но в теле не используется. `grep` имя параметра в теле → 0 → мёртв. Эталон-находка: `IDGenerator` инжектился, но не дёргался; `id_registry` отсутствовал; мёртвые импорты рядом.
- **Недёрнутый метод:** `grep -rn "\.log_event(" core/ server.py` → 0 вызовов = мёртв (D24).
- **Мёртвый импорт:** импортируется, не используется (bandit/pyflakes ловит).

**Лечение:** либо реально подключить зависимость, либо удалить параметр+импорт. Не оставлять «на будущее» без вызывающего — это гниёт и врёт о зависимостях.

## 5. Stringly-typed drift (🟡, G15)

**Инвариант:** конечные множества (статусы, коды, типы фактов) — `Literal`/реестр, не свободные строки.
- ✅ `TaskStatus.status: Literal["pending","running","success","error",...]`; коды из `KNOWN_ERROR_CODES` + `server_reactions.yaml`; типы фактов из `KNOWN_FACT_TYPES`.
- ❌ `status = "sucess"` (опечатка пройдёт), код реакции, которого нет в реестре (D4 — рассинхрон), `Fact(type="ValueSet")` мимо `KNOWN_FACT_TYPES` (D25).

**Как искать:** строковые литералы статусов/кодов в коде, не сверенные с реестром; новые коды/факты, не добавленные в `server_reactions.yaml`/`KNOWN_*` (D4/D25 discipline). Замечание: конкретные захардкоженные *значения* (пути, пороги, имена) — соседний скилл `anti-hardcode`; здесь именно про **типизацию словаря** статусов/кодов.

## 6. Bounded Context (🟡)

- Код/конфиг — в git-дереве сервера; данные — только `workspace/` (не git).
- `config/` = декларации, не логика; логика — `core/`; обёртки — `tools/`/`server.py`; тесты — только `tests/` по структуре.
- Инструмент не читает/пишет чужой контекст напрямую. Сверка — memory `project-rules` §2 (матрица размещения).

**Анти-паттерн:** `_SESSION_LOG.md` пишется в корень репо (данные в дереве кода) — известный footgun; рантайм-данные должны бы жить в `workspace/`.

---

## 7. Простота / altitude (🟡)

- Лишний слой абстракции (фабрика ради одного класса), дублирование, «умный» однострочник, комментарий, повторяющий код.
- Код должен читаться как соседний: те же имена, идиомы, плотность комментариев.
- **Не** плоди обобщение «на вырост» под один случай (оверинжиниринг — зеркало оверфита в тестах).

---

## 8. Эффективность в меру проекта (⚪)

Сервер I/O-bound, малый масштаб — **микрооптимизация не нужна**. Реальные цели:
- не открывать один файл/`.xlsx` дважды за одну операцию (кэшировать в пределах вызова);
- busy-loop без сна — дефект; пауза и backoff объявляются в `config/media_tasks.yaml`, не зашиваются в цикл;
- `O(n²)` терпимо, если n мал и не растёт; если растёт (реестр связей, дерево структуры) — прикинуть.
- атомарность важнее скорости: запись через temp+rename (уже эталон `_atomic_write_json`) не «оптимизировать» в прямую запись.

Читаемость и корректность > мнимая скорость. Оптимизируй только измеренное узкое место.
