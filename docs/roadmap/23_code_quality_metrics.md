# 23 — Метрики качества кода: что мерить, чем, какой ценой

> **Зачем.** Директива владельца «уменьшать код» и сторож антихардкода были без цены, радиуса и
> способа мерить, поэтому оставались лозунгом. Здесь замер кандидатов НА НАШЕМ дереве и НА НАШЕЙ
> разметке — чтобы сторож качества строился на доказанном, а не на репутации метрики.
>
> **Все числа собраны заново командами ниже.** Число в этом файле устаревает молча.

## Метод: почему замер, а не выбор по репутации

Разметку дал реестр находок: **315 строк `F#`, из них 112 назвали хотя бы один живой файл, всего
99 файлов**. Это не «баги вообще» — это места, где МЫ находили дефекты. Дальше каждая метрика
проверялась вопросом: указывает ли она на эти файлы раньше, чем мы туда посмотрели.

```
.venv/bin/python -c "import ast,json,pathlib,subprocess,collections"   # весь замер на stdlib + git
```

Ни одна мерящая библиотека (`radon`, `vulture`, `mutmut`, `lizard`, `pylint`) в `.venv` **не
установлена** — всё измерено `ast` и `git log`. Это осознанно: решение о зависимости отдельное,
и принимать его до замера значило бы платить за инструмент, полезность которого не проверена.

## Замер 1 — что предсказывает НАШИ находки

Базовая доля: из 179 файлов `.py` метку дефекта носят **69 (38.5 %)**.

| метрика | точность топ-20 | подъём над базой |
|---|---|---|
| `churn` — сколько коммитов трогали файл | 85 % | **2.2×** |
| `loc` — строк | 80 % | 2.1× |
| `hotspot` = churn × когнитивная | 80 % | 2.1× |
| `cyclo` — цикломатическая | 65 % | 1.7× |
| `cog` — когнитивная (SonarSource, упрощённо) | 65 % | 1.7× |
| `fanin` — сколько модулей импортируют | 35 % | **0.9× (хуже случайного)** |

## Замер 2 — что остаётся, когда размер держат постоянным

Верхний рейтинг сам по себе врёт: крупный файл содержит больше всего, включая находки. Поэтому
файлы разбиты на три трети по размеру, и внутри КАЖДОЙ трети сравнивалась верхняя половина по
метрике с нижней.

| метрика | мелкие | средние | крупные | разделяет |
|---|---|---|---|---|
| `churn` | 30/20 % | 40/20 % | **83/40 %** | 2 из 3 |
| `hotspot` | 30/20 % | 43/17 % | 69/53 % | 2 из 3 |
| `cog` | 33/17 % | 27/33 % | 62/60 % | 1 из 3 |
| `cyclo` | 30/20 % | 27/33 % | 66/57 % | **0 из 3** |
| `fanin` | 27/23 % | 27/33 % | 52/70 % | **0 из 3, инвертирована** |

Плотность находок на 1000 строк: мелкие **9.8**, средние **4.3**, крупные **5.0**.

**Три вывода, которые меняют план:**

1. **Цикломатика сверх размера не добавляет ничего (0 из 3).** Сторож на пороге `C901` был бы
   театром: он назвал бы крупные файлы, которые и так видно по размеру.
2. **`churn` — единственная метрика с сигналом сверх размера**, и сильнее всего у крупных
   (83 % против 40 %). Дорого ломается то, что часто трогают, а не то, что запутанно.
3. **`fan-in` инвертирован**: часто импортируемое у нас как раз устойчиво — это объявленные ядра.
   Правило «много зависимостей = риск» здесь дало бы ровно обратный ответ.

**Оговорка, без которой числа врут.** Метка — «находка НАЗВАЛА файл», а искали мы чаще там, где
работали. `churn` поэтому частично предсказывает, ГДЕ МЫ СМОТРЕЛИ. Разделение внутри одной трети
по размеру (83/40) этот конфаунд ослабляет, но не снимает. Честный статус: сильнейший кандидат,
а не доказанный закон.

## Замер 3 — признаки ПРОЧНОСТИ (ломается ли код на первом исключении из образца)

Это ответ на пример владельца: «улики мерили по признаку, а не классу — прочности нет, первое же
исключение ломает». Признак структурный, а не размерный, поэтому конфаундом размера не заражён.

| признак | мест в дереве | у болевших / у чистых, на 1000 строк | вывод |
|---|---|---|---|
| `isinstance` — ручной разбор по типу | 309 | **10.5 / 6.1** | **РАЗЛИЧАЕТ** |
| строка-как-тип (`== "литерал"`) | 979 | 28.9 / 25.7 | не различает |
| признак вместо класса (`hasattr`/`getattr`) | 56 | 1.3 / 2.1 | инвертирован |
| промах-как-ветка (`except AttributeError/KeyError`) | 1 | — | уже чисто |

**Что это значит для директивы.** Принцип «класс, а не признак» верен, но в НАШЕМ дереве
`hasattr`-диспетчер — 56 мест, и они не там, где мы болели. Живая форма той же болезни у нас
другая: **ручной разбор по типу через `isinstance`**, и он с находками связан. А самый массовый
кандидат (979 сравнений со строкой) не различает вовсе — то есть «хардкод строкой» в нынешнем
грубом замере не является предиктором и правило по нему стоило бы дорого при недоказанной пользе.

## Цена, зона и радиус — то, чего у директивы не было

**Радиус (где вообще лежит измеримый код):**

| дерево | файлов | строк |
|---|---|---|
| сервер | 102 | 13 988 |
| тесты | 45 | 12 870 |
| сторожа | 18 | 6 022 |
| хуки | 10 | 1 905 |
| вне деревьев | 4 | 637 |

**Цена кандидатов — сколько мест правило назовёт СЕГОДНЯ (это и есть будущий потолок):**

| кандидат | сервер | сторожа | тесты | хуки | ИТОГО |
|---|---|---|---|---|---|
| `isinstance`: ручной разбор по типу | 84 | **182** | 39 | 4 | **309** |
| горячая точка: часто правится и крупнее медианы | 7 | 2 | 7 | — | **16** |

Плотность `isinstance`: сторожа **30 на 1000 строк**, сервер **6**. Дерево, которым мы судим
проект, в пять раз гуще разбирает типы руками, чем сам проект.

## Что из этого следует для сторожа качества

| ось-кандидат | чем мерить | цена (потолок) | зона | риск |
|---|---|---|---|---|
| **горячая точка** — часто правится И крупнее медианы | `git log --name-only` + `ast` | 16 файлов | все четыре дерева | метка предсказывает «где мы смотрели»; ось обязана быть ПОКАЗОМ приоритета, а не отказом |
| **ручной разбор по типу** — `isinstance` вместо объявления/протокола | `ast` | 309, из них 182 у сторожей | начать со `сторожа` — там гуще и там же горячая точка №1 | часть `isinstance` законна (разбор внешнего ввода); порог без исключений заглушит сторожа |
| ~~цикломатика~~ | — | — | — | **отвергнута замером**: 0 из 3, сверх размера не добавляет |
| ~~fan-in~~ | — | — | — | **отвергнута замером**: инвертирована |
| ~~строка-как-тип~~ | — | 979 | — | **отложена**: замер грубый и не различает; сначала уточнить замер, потом решать |

**Порядок, который следует из цены.** Сначала «горячая точка» — она стоит 16 файлов и не требует
правок кода, только показа. Потом `isinstance` в дереве сторожей (182 места) — там и плотность
выше, и файл `scripts/guards/invariants.py` одновременно горячая точка №2.

## Чем собрать заново

```bash
# разметка: какие файлы называли находки
grep -cE '^\|\s*~?~?F[0-9]+' docs/roadmap/02_findings.md
# churn по файлу
git log --format=%H --name-only | grep '\.py$' | sort | uniq -c | sort -rn | head -20
# плотность isinstance по деревьям
.venv/bin/python -c "import sys;sys.path.insert(0,'scripts/guards');import _evidence;print(_evidence.деревья())"
```

Полный замер лежал в черновиках сессии и воспроизводится скриптами из этого файла: `ast` для
метрик, `git log` для churn, реестр находок для разметки. Новых зависимостей не требуется.
