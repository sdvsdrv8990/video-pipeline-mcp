### Сессия 19 (доп. 2) — директива владельца: цепочка выводится из каталога назначения (S18-h, F63/F64/F65)

**Формулировка владельца:** с нуля вопросов нет; в **уже существующей** структуре сервер обязан сам понять
по каталогу, какие уровни пропущены и какие ID уже готовы (ID личного канала, ID канала конкурента) — знать
дерево конкретного проекта, где сетки может не быть. Для переноса — присваивать ID цели **до** переноса,
чтобы ИИ проверил корректность и починил руками.

**Проверено прогонами — ломается именно при создании, а не только при переносе:**
- **F63 🔴** `structure_create` зовёт движок с `parent_ids=None` **жёстко** (`tools/structure/__init__.py:29`),
  в схеме инструмента параметра нет. Прогон по сценарию владельца: сессия 1 создала `ниша→сетка→канал`,
  сессия 2 создаёт видео внутри канала → путь верный, **`parent_ids=[]`**. Цепочка возникает **только**
  внутри одного greenfield-вызова, то есть ровно там, где вопросов и не было.
- **F64 🟠** у `LinkRegistry` нет `find_by_path` — спросить «кто живёт по этому пути» нечем, containment-
  резолюция стоять не на чем; адресация `(тип, имя)` в иерархии неоднозначна (два `video:intro` в разных
  каналах → `VALIDATION_ERROR «Неоднозначно»`, ломает `structure_link`/`migrate`).
- **F65 🟠** `fs_move`/`fs_rename`/`fs_delete` идут мимо реестра (`migrate` вызывается только из
  `structure_migrate`): после переноса путь в реестре протух, каталога на диске нет, а
  `check_integrity` даёт **`0 issues`** — она не сверяет путь с диском.

**Дизайн — `13` §S18-h.** Один резолвер `resolve_chain(каталог) → {chain, skipped, owner_id, new_segment,
unresolved}` обслуживает и создание, и перенос. Предки берутся **готовыми** и никогда не перегенерируются
(молчаливый второй ID для существующего каталога = раздвоение личности, запрещено явно); тип нового узла —
из `children[].container` шаблона, а не из хардкод-карты путей; пропуск уровня — по факту, отсутствие
обязательного родителя → ORPHAN + короткая цепочка; каталог на диске без записи в реестре → `unresolved`
и явное усыновление (`EntityAdopted`), а не выдумка. Реестру нужен `find_by_path` + инвариант «один каталог
= максимум одна сущность своего уровня» при регистрации. `structure_resolve(path)` (readonly, тот же
резолвер) — способ дать ИИ ID заранее в существующей структуре (S18-g п.1). Перенос: resolve → показать
дельту → move → `migrate` одной операцией с откатом; безопасность починки руками держится на неизменности
собственного сегмента (S18-g) — неверная раскладка портит адрес, не личность.

**Тесты:** кода не трогал (доки) → baseline держится (`pytest -m "not live"` 14 passed).

### Сессия 19 (доп. 1) — директива владельца: сквозная иерархия ID сверху вниз (S18-g, F60/F61/F62)

**Формулировка владельца:** создание файла — ручное или шаблонное, до или после появления таблиц —
обязано **заранее сказать ИИ**, что ID присвоит сервер, и вернуть имя+адрес+ID (или список, если файлов
несколько). ID строится сверху вниз (сетка → канал → видео), уровни **условны** (нет сетки → сегмента нет),
а при наличии нашего личного канала все сущности **включая конфиги** несут ещё и его ID — «конкурентом
какого канала» они считаются. Собрать в единую систему, в том числе для поиска в ФС и в таблицах.

**Проверено прогонами — все три опасения подтвердились, одно жёстче:**
- **F60 🔴** — поиск по ID в ФС мёртв: `_extract_id` (`fs_searcher.py:320`) читает **имя файла**, а ID живут
  в фактах и `LinkRegistry`; имена задают шаблоны (`channel_data.xlsx`, `read.json`). Прогон: 8 файлов,
  `entity_id=''` у **всех**; `id_pattern` с **реальным** `VID`-ID → **0 результатов**. Файловый близнец F57.
  Побочно: пример в схеме `VID_*` — glob, а потребляется `re.search`.
- **F61 🔴** — две вселенные файлов: `structure_create` даёт ID + реестр + факт `NodeCreated`, а
  `fs_create_file`/`fs_write_file`/`fs_create_python_script`/`fs_create_project_structure` — **ни ID, ни
  реестра**, ответ `{"created": path}`. Ни одно описание создающего инструмента про ID не говорит.
- **F62 🟠** — иерархия есть в путях и `parent_ids`, но не в ID (плоский `VID_<uuid>`); подстановка
  `{наш_канал}` объявлена в `network.tpl.yaml` и **не реализована** (прогон: `networks/net1/competitors/compX`);
  иерархия задана в **4 местах** (`children`-ссылки, `REQUIRED_PARENT_TYPE`, `ENTITY_PATH_PATTERNS`, 2 копии префиксов).

**Дизайн — `13` §S18-g.** Квалифицированный ID = цепочка предков + собственный сегмент
(`NICHE_…/NET_…/CH_…/COMP_…/CVID_…`), пропуск уровня = отсутствие сегмента без заглушек. Ключевое решение
снимает конфликт «поздняя привязка ломает ссылки»: **собственный сегмент неизменен, цепочка вычисляема** из
реестра → `structure_link`/`migrate` переквалифицируют адрес, а `row_id` (S18-b, владелец = собственный
сегмент) и внешние ссылки живут. Состав уровней объявляется блоком `id:` в каждом `*.tpl.yaml` (проектируется
под шаблон индивидуально) — он же единственный источник префиксов (снимает F41/F46) и допустимых родителей.
Укорочение сегмента (`scoped8`) разрешено **только** вместе с `check_unique` в реестре — иначе возвращается D9.
Создание получает единый пост-контракт: `entities: [{id,type,name,path,chain,owner_id}]` + фиксированная
строка в `description`; ручные файлы получают владельца **по вместимости**. Поиск в обеих вселенных получает
общий словарь `owner_id` + `chain_prefix` (префикс цепочки = поддерево).

**Тесты:** кода не трогал (доки) → baseline держится.
