### Сессия 23 (доп. 7) — «не влезает» перестало быть приговором; свой слой ужат до политики

**Замечание владельца:** решение под fp16 не масштабируется, под крупные модели поддерживать
станет сложнее; может, есть готовое. Проверено — готового почти всё: diffusers 0.39 принимает
`variant`/`dtype`/`device_map`/`max_memory`/`quantization_config`, умеет три вида выгрузки,
знает 7 движков квантизации. Значит `variant` — параметр библиотеки, а не наш слой, и ответ на
«модель больше карты» — выгрузка, а не второй набор весов.

**Что убрано из нашего кода.** `variant` теперь берётся из ОПИСИ (`registry.model_entry`), строка
канала — только перекрытие: требовать столбец от ИИ значило ронять вызов из-за незаполненного
поля (это и был F80). Загрузочные параметры идут объявленной картой `local.gpu.load_from_row`
(столбец строки → параметр библиотеки): новый рычаг diffusers добавляется строкой в YAML, а не
веткой в коде. Чего в карте нет — в загрузчик не уезжает.

**Что добавлено — тонкий слой политики.** `hardware.placement()` решает «целиком или с выгрузкой»
по объявленному `local.gpu.oversize` (`error | model_offload | sequential_offload`), применяет
решение адаптер. Перенос и выгрузка взаимоисключающи (у выгруженного пайплайна `.to()` ругается
сама библиотека) — поэтому ровно одна ветка из трёх. Вердикт каталога вместо голого `no` несёт
`fit.oversize` с ценой режима.

**Доказано живьём, а не рассуждением** (порог поднят декларацией, чтобы настоящая sdxl-turbo
«не влезла» в настоящую карту): `model_offload` → **1.5 с/кадр при VRAM +451 МБ** против
0.4 с/+9276 МБ целиком и 7.7 с на процессоре. То есть впятеро быстрее процессора при 5% занятой
памяти карты. По дороге поймана своя же ошибка проводки: у методов выгрузки первый позиционный
аргумент — `gpu_id`, а не устройство (`cuda:cuda`); отказ при этом вышел громким и с настоящей
причиной — как и задумано.

**Чего НЕ взяли и почему.** `accelerate.commands.estimate` (готовая оценка памяти по репозиторию
HF) знает только `timm`/`transformers` — для diffusers-моделей наш `FitEstimator` незаменим, для
будущих whisper/LLM заменится. `dtype="auto"` в diffusers не поддержан, в отличие от transformers.
Квантизацию сознательно не заводили: на ROCm/gfx1101 её пришлось бы проверять живьём каждый раз,
а качество картинки падает — ровно то усложнение, которого просили избежать.

**Приёмка:** `test_providers` 178 → **189/189**, включая живую выгрузку на карте и проверку, что
`variant` приходит из описи (в строке живого теста его больше НЕТ — регрессия упадёт сразу).
Гейт 16 passed; `test_firewall` красный до и после (integration).

### Сессия 23 (доп. 5) — видеокарта читается без root, и её память вошла в вердикт

**Замечание владельца:** локальные модели крутят на видеокарте, а не на процессоре; карта AMD.
Вопрос был — можно ли без root прокинуть ИИ адаптер и его доступную память.

**Можно, и без единой утилиты.** Ядро выкладывает карту в `/sys/class/drm/card*/device` правами
`0444`: `uevent` даёт драйвер и PCI-номер, а `amdgpu` кладёт рядом `mem_info_vram_total/used` —
объём и занятое. Имя берётся из системной `pci.ids`. Проверено под uid 1000: `amdgpu`,
`1002:747e` → `Navi 32 [Radeon RX 7700 XT / 7800 XT]`, 16 152 МБ свободно из 17 163. `nvidia-smi`
остался вторым источником (у nvidia объёма в sysfs нет), но перестал быть единственным — прежняя
формулировка «карта видна только через nvidia-smi» была неверна для всех остальных драйверов.

**Видеть память карты ≠ уметь ею считать.** У каждой карты теперь `usable` с причиной: сборка
`torch 2.13.0+cu130` не увидит AMD, для неё нужна `+rocm`. Тег читается из `<пакет>/version.py`
ТЕКСТОМ, без импорта (импорт torch — секунды на каждый список; в метаданных дистрибутива тега нет
вовсе — там голое `2.13.0`, на это напоролся первый вариант). Соответствие «драйвер → нужный тег»
объявлено в `config/providers.yaml → local.gpu`, не зашито.

**Вердикт считается по той памяти, до которой расчёт дотягивается.** `FitEstimator.pool()` берёт
карту, если она доступна, иначе ОЗУ; недоступная карта не подмешивается в вердикт (обещать чужую
память нельзя), а возвращается вторым числом `fit.on_gpu` с `blocked_by` — иначе про 16 ГБ рядом
никто бы не узнал. В каждом вердикте теперь названо, ПО КАКОЙ памяти он посчитан.

**F79 (новая, 🟠, не чинил):** карта доходит до ИИ, но исполнитель считает на CPU при любом
железе — в `diffusers_local.py` пайплайн никуда не переносится (`.to(device)` нет во всём каталоге
провайдеров). Пока сборка не совпала, расхождение ненаблюдаемо. Чинится после установки
`torch+rocm` — доказать перенос на этой машине сейчас нечем, а код вслепую тут хуже, чем запись.

**Тесты:** `test_providers` 160 → **169/169** (поля карты, причина у каждой, вердикт по ОЗУ при
недоступной карте, `on_gpu` с причиной — на синтетическом железе, чтобы не зависеть от машины).
Гейт: 16 passed, `test_firewall` красный ДО и ПОСЛЕ правки (integration, нужен живой сервер) —
проверено `git stash`. `ruff core/ tools/ scripts/` — только F76.

### Сессия 23 (доп. 4) — один источник локальных моделей + «влезет ли на это железо»

**Каталог-декларация снят (указание владельца).** В `config/providers.yaml` жил рукописный
`local.catalog` с тестовыми моделями — теперь его нет: локальные модели приходят ОДНИМ путём
(живой каталог → установка → опись `vendor/models/installed.yaml`). Одна модель больше не может
быть описана дважды по-разному, и на вопрос «откуда она взялась» есть один ответ. Уже лежавшие на
диске веса усыновлены в опись, чтобы не стать сиротами; `models.py pull` теперь восстанавливает
веса ПО ОПИСИ (она переезжает с машиной, гигабайты — нет).

**Число параметров пришло в каталог.** Общее — из метаданных `safetensors`, одним запросом на весь
список (`expand`), а не по запросу на модель. Активное — только если модель сама его объявляет
(это про MoE): вычислять «на глаз» нельзя, придуманное число выглядит как факт. Не объявлено —
пусто, и так и написано.

**Железо читается БЕЗ root — проверено, а не предположено.** `/proc/meminfo` доступен любому
пользователю, причём важен `MemAvailable`, а не `MemFree`: ядро отдаёт кэш под запрос, и «свободно»
систематически занижает. Ядра даёт сам процесс, свободное место — статвызов, лимит контейнера —
файл cgroup, если он есть. Root нужен для серийников и DMI (`core/integrity` уже упирался в это),
но для «влезет ли модель» они не нужны. Видеокарта видна только через `nvidia-smi`; его отсутствие
означает «НЕ проверено», и это написано прямо — пустой ответ врал бы уверенностью.

**Вердикт считает сервер, а не человек.** Параметры × разрядность + запас на активации →
сравнение с доступной памятью → `fits` / `tight` / `no` / `unknown`, с числами, по которым видно
почему. Пороги (`dtype_bytes`, `overhead`, `tight_ratio`) объявлены в конфиге: на другой машине
«впритык» начинается в другом месте. Разрядность решает: та же модель в fp16 требует вдвое меньше,
чем в fp32, и вердикт из-за этого меняется на противоположный. Нет числа параметров — `unknown`,

параметров не с чем сравнить); в терминале — `python scripts/models.py hardware` и колонки
параметров с вердиктом в `local`. Живой прогон: `Z-Image-Turbo` 6.2B → `no` (нужно 33 ГБ при 24
доступных), `stable-diffusion-v1-5` 0.9B → `fits`.

### Сессия 23 (доп. 2) — установка под наблюдением + рекомендация облака данными

**Установка перестала быть «вызовом на гигабайты».** Веса качаются минутами и рвутся на середине,
поэтому `media_model_install` теперь ЗАПУСКАЕТ загрузку и отдаёт `install_id`, а ход прозванивается
`media_install_status`. Четыре исхода и ни одного молчания: `running` · `done` (с путём) ·
`failed` (код + причина) · **`stale`** — байты не растут дольше объявленного срока, значит сервер
перезапустили или поток умер, и «идёт» здесь было бы враньём. Повтор дешёвый: загрузчик
продолжает с места обрыва, скачанное не выбрасывается.

**Прогресс меряется ПО ДИСКУ** — тем же приёмом, что и приёмка файла у провайдера: загрузчик
способен отрапортовать и оборваться, а выросшие байты не врут. Считается ПРИРОСТ от того, что
лежало на старте (иначе «прогресс» показывал бы размер всего каталога моделей), и смотрится не
только каталог моделей, но и кэш загрузчика — файл сперва ложится туда.

**Это не планировщик.** Поток живёт ровно столько, сколько идёт эта установка, и умирает вместе с
ней; между запросами клиента ничего не тикает (S15 в силе). Отвалившийся клиент установку не
теряет и не спасает — ровно та же граница, что у задачи провайдера.

**Чем исполнять облако — сервер СОВЕТУЕТ, а решает канал.** Совет пришёл в существующий канал
рекомендаций (`config/recommendations.yaml` → `media_provider_status.choice`), то есть данными:
картинки — **OpenAI `gpt-image-2`** (проверено на сайте OpenAI: это актуальная старшая модель
линейки, эндпоинт `/v1/images/generations`), озвучка — **ElevenLabs `eleven_v3`** или подешевле
**OpenAI `gpt-4o-mini-tts`**, плюс совет держать локальных провайдеров последними в цепочке
fallback. Каждый совет исполним `table_update` по строке — новой двери не заводили. Имён моделей
в коде нет: регрессия проверяет грепом по трём модулям.

⚠️ **Замечено при проверке:** реестр установленного шлюза (litellm 1.96.2) знает линейку до
`gpt-image-1.5` — `gpt-image-2` в нём ещё нет. Имя модели уходит провайдеру из строки канала как
есть, поэтому это не блокер, но `media_models(scope='online')` его не покажет, пока шлюз не
обновят. Сказано прямо в тексте самого совета.

**Найдено тестом и починено:** нечитаемый файл ключей ОДНОГО канала (восстановлен из чужого
бэкапа, потерян `instance_secret.key`) ронял ВЕСЬ `media_provider_status` в `INTERNAL_ERROR`.
Теперь это состояние одного ключа: `unreadable` + код + причина, остальные провайдеры видны.
Тот же закон, что «отказ по одному ресурсу не прячет остальные».

**Приёмка:** `test_providers` 124 → **139/139** (§16 четыре исхода установки, двойная загрузка
одних весов отбита, замершая названа прерванной; §16b советы приходят и исполнимы, имён моделей
в коде нет, нечитаемый ключ не ослепляет отчёт). Инструментов 67, остальные наборы без изменений,

### Сессия 23 (доп. 1) — каталог моделей: список живой, установка проверяет, ЧТО кладёт на диск

**Разведено на входе (проверено по документации LiteLLM, не по памяти):** ключ самому LiteLLM не
нужен — он спрашивает ключи ПОСТАВЩИКОВ; локальная модель зовётся через него вовсе без ключа.
Но для НАШИХ локальных моделей он не даёт ничего: в его `image_generation` нет локального
Stable Diffusion, в `speech` нет ни одного локального движка вообще. piper и sd-turbo работают
в процессе сервера, без HTTP и без ключей. Значит LiteLLM полезен как ЗНАНИЕ об облаке (реестр
моделей), а исполняет облако адаптер, которого пока нет.

**Онлайн-список берётся из реестра шлюза, а не из документации.** 3019 записей лежат офлайн в

или символ. `python scripts/models.py online --kind tts` показывает их **без ключа** — ключ
нужен для вызова, а не для списка. Заодно видно, кто вообще умеет нужный вид ресурса, ДО того
как заводить у него счёт.

**Локальный список — живой каталог с отсевом по декларации.** Голоса: индекс `rhasspy/piper-voices`

### Сессия 23 — ключи провайдеров: лежат в канале, зашифрованы, инструментам недоступны

**Задача владельца:** чтобы ставить провайдеров, которым нужен ключ, нужен защищённый файл ключей
НА УРОВНЕ КАНАЛА, и модель не должна получить значение никаким способом — включая захват экрана
владельца в момент ввода.

**Где лежит и почему там.** `<канал>/.secrets/provider_keys.enc`: ключ — свойство канала (у каждого
свои счета и свои поставщики), поэтому он там же, где данные канала. Шифрование — Fernet, файл
`0600`, каталог `0700`, запись атомарная (половины файла ключей не бывает).

**Запрет стоит в ЕДИНОЙ точке путей, а не в хендлерах.** `core/paths` — тот же choke-point, что и
containment (G17): закрытый каталог даёт `SecretAccessError` → код `SECRET_ACCESS_DENIED`. Если бы
запрет писался в каждом инструменте, первый забывший открыл бы дверь. Отдельно закрыты ОБХОДЧИКИ:
листинг дерева и поиск ходят по диску мимо резолвера — «невидим для чтения, но виден в списке» это
половина защиты. Проверено живьём на шести дверях (чтение, запись, удаление, перенос,
переименование, память) + дерево + два поиска (по имени, по расширению, по содержимому).

**Fail-closed.** `firewall.yaml → secret_paths.dirs` может РАСШИРИТЬ список закрытых имён, но не
отменить встроенный минимум: он живёт в коде, потому что правка одной строки YAML не должна тихо
открывать ключи. Регрессия проверяет обе стороны.

**Ввод ключа — только владелец и только вручную.** `scripts/set_provider_key.py`: имя провайдера
подставлено, поле значения пустое, ввод скрыт (`getpass`) — на экране не появляется ни символа,
поэтому захват экрана и запись сессии ключа не покажут. Шифрование происходит ДО записи, в память
скрипта; в переписке значение не живёт вовсе. Ротация ЗАМЕНЯЕТ старый ключ (два действующих ключа
на одного поставщика — вопрос «каким сейчас платят», а на него не должно быть двух ответов);
прежний отпечаток остаётся следом замены.

**Что видит ИИ.** `media_provider_status` показывает по каждому провайдеру `required/present/
fingerprint/updated` и команду для владельца — по отпечатку видно, ТОТ ли ключ стоит, и
восстановить его нельзя. Нет ключа → `PROVIDER_KEY_MISSING`: «прав читать или записывать ключ у
меня нет, вставляет владелец вручную вот этой командой», плюс обходной путь — поставить в строке
канала провайдера без ключа (`table_update`). Ключ нужен или нет — объявляет СЕРВЕР
(`adapters.by_provider`), не строка канала: строку правит ИИ, и «ключ не нужен» не должно быть его
решением. Облачные `ElevenLabs`/`OpenAI`/`Fal` объявлены как требующие ключ и пока БЕЗ адаптера —
сервер скажет об этом прямо, а не сделает вид, что вызвал.

**Последний рубеж.** Провайдер способен процитировать присланный ключ в тексте отказа
(`invalid api key 'sk-…'`) — `redact` меняет значение на отпечаток. Проверено двойником, который
это делает нарочно.

**Честная граница (записана в модуле и в плане `15`):** шифрование на диске защищает от
инструментов сервера и от чужих глаз в кадре, но не от того, у кого есть shell на этой машине —
ключ шифрования лежит рядом (`instance_secret.key`, `0600`, вне git, ловится правилом `*.key`).
Для модели, работающей через MCP, shell недоступен, и граница жёсткая. Веб-версия с вводом ключа
в браузере — следующий шаг; в терминале ввод остаётся ручным по построению.

**Приёмка:** `test_providers` 82 → **109/109** (§14 периметр, §14b ключ доходит до провайдера и не
появляется в данных/фактах/журнале), остальные наборы без изменений, гейт 16 passed. Мутации
M92–M97: снять запрет в точке путей · вернуть файл в поиск · вернуть его в листинг · писать ключ
открытым текстом · вызывать без ключа молча · не вычищать ключ из текста отказа.

**Побочно:** 15 мест `except ValueError → PATH_ESCAPE` в четырёх группах инструментов сведены к
`ctx.err_path(exc, msg)` — закрытый каталог и выход за область теперь РАЗНЫЕ причины в ответе:
модель не должна искать обход там, где двери просто нет.
