### Сессия 22 (доп. 12) — две правки по указанию владельца: F77 (адрес копии шаблона) и F78 (хардкод в адаптерах)

**Оба замечания владельца подтвердились прогоном, оба закрыты.**

**F78 — «локальные модели прописаны в коде вместо конфига».** Проверил по коду: выбор провайдера
и модели действительно шёл из данных (строка канала → `adapters.by_provider` → адаптер), НО внутри
адаптеров сидело два класса хардкода. Первый — `SUBDIR = "tts"/"img"`: раскладка каталога весов
дублировала `local.catalog[].dest`, и правка `dest` в декларации молча разошлась бы с местом, куда
смотрит код (класс D2 — конфиг, который врёт). Второй — числа за модель: `DEFAULT_SIZE = 512`,
`guidance_scale=0.0`, `steps=1`; `guidance=0` верен для дистиллированных пошаговых моделей и портит
картинку у обычных, то есть код решал за модель.
**Стало:** путь к весам отдаёт реестр по декларации (`id → path`; имя вне каталога = путь внутри
корня весов; containment на обоих путях), адаптер получает `registry` и не знает раскладки вовсе;
параметры генерации собираются только из объявленных столбцов строки, чего в строке нет — не
передаётся, и решает модель. Строка канала называет модель по `id` из каталога.

**F77 — «копия шаблона падает не туда».** Владелец прав, и хуже, чем прозвучало: `structure_customize`
принимал ЛЮБОЙ адрес. `path=""` клал копию в корень рабочей области, а несуществующий адрес —
создавал каталог и сеял шаблоны в него. Резолвер ищет `.templates/` ВВЕРХ по дереву, поэтому копия
выше канала молча становится законом для всех сущностей ниже: правка «под один канал» меняла бы
соседние.
**Стало:** адрес обязан быть зарегистрированной сущностью (`link_registry.find_by_path`), иначе
`ENTITY_NOT_FOUND` с объяснением и `structure_assign_id` в recovery; в успешном ответе названы
владелец копии (`owner`) и её область действия (`scope_note`) — область перестала быть невидимой.
Ниша осталась законным адресом: адаптация уровня — осознанное решение, а вот корень — нет.

**Приёмка:** `test_providers` 74 → **82/82**, `test_structure` 237 → **242/242**, остальные наборы
без изменений, эталон инструментов обновлён (описание и схема `structure_customize`), гейт 16 passed.
Мутации: **M90** (адаптер снова знает раскладку) и **M91** (копия ложится по любому адресу) краснеют.

### Сессия 22 (доп. 11) — провайдеры, шаг 3: расход учтён, файл забирается, локальные модели исполняют

**Учёт расхода (`core/providers/usage.py`) — первым, как и планировалось.** Единица меряется
СТРОКОЙ канала (`usage_unit`: вызов/символ/файл), способов измерения ровно три и они в коде,
назначение способа провайдеру — данные. Неизвестная единица = отказ `USAGE_UNIT_UNKNOWN`, а не
тихий ноль: тихий ноль означал бы, что лимит не наступит никогда.

**Счётчик пишется МИМО очереди — намеренно.** `write.json` это дверь для правок ИИ: они копятся и
применяются осознанным `json_execute_queue`. Положи расход туда — он не двигался бы до чужого
вызова, а применение утащило бы вместе с ним ВСЕ накопленные чужие операции. Прибавка идёт
точечно в снапшот (containment `StateManager` тот же), и регрессия проверяет, что чужая очередь
осталась нетронутой. **Петля замкнулась:** расход добивает `daily_limit` → резолвер сам уходит на
запасного, без единой правки руками.

**Исполнение (`media_generate`) — 64-й инструмент.** Строка канала → адаптер → файл в рабочей
области → приёмка по диску → расход. Синхронный провайдер отдаёт файл сразу; асинхронный —
идентификатор задачи, и прозвонка идёт ВНУТРИ этого же вызова (демона нет, S15). Если провайдер
отдал только ссылку — файл забирает сервер сам.

**Имя провайдера — данные, путь к коду — конфиг** (`config/providers.yaml → adapters.by_provider`
+ ограничение корня импорта). Иначе строка таблицы, которую правит ИИ, выбирала бы, какой Python
импортировать: данные исполняли бы код.

**Загрузка по ссылке (`core/providers/download.py`).** Ссылку даёт провайдер, значит она приходит
ИЗВНЕ: схема и адрес проверяются ДО запроса (запрет петли, приватных и link-local адресов —
иначе сервер своими руками сходит туда, куда клиент не достаёт), предел размера считается ПО ХОДУ
записи, недописанный файл удаляется, а не выдаётся за результат. Тип файла результата проходит
тот же `write_allowlist`, что и любая запись: результат провайдера не привилегирован (`response_format: sh`
→ `FILE_TYPE_FORBIDDEN`).

**Локальные модели — чтобы «работает» перестало быть словом.** Две: озвучка `piper`
(`ru_RU-dmitri-medium`, 61 МБ) и картинки `sd-turbo` (fp16, 3.9 ГБ, один шаг, CPU ≈ 12 с). Веса
лежат в `vendor/` (в `.gitignore`) и тянутся `scripts/fetch_local_models.py` по декларации
`local.catalog` — в git уходит объявление, а не гигабайты. Имя модели из строки канала проходит
containment: `../../.env` в поле `model` читало бы чужое. Нет весов → `LOCAL_MODEL_MISSING` с
названной командой, а не тишина. В дефолтах декларации локальные провайдеры стоят последними в
цепочке fallback — она теперь кончается тем, что исполнимо без ключей.

**Общая загрузка деклараций** (`core/providers/declaration.py`) — три копии «файл/битый/mtime»
свелись в одну: расхождение копий вылезало бы как «конфиг правлю, а сервер по-старому».

**Приёмка:** `test_providers` 43 → **74/74** (живые прогоны обеих локальных моделей + двойники
асинхронного провайдера: с собственной загрузкой и «только ссылка»). Мутации краснеют: M86 (снять

### Сессия 22 (доп. 10) — цикл ожидания задачи провайдера и приёмка загрузки

**Разведено на входе:** опрос ВНУТРИ вызова — не планировщик. Решение владельца S15 (демона нет)
в силе: цикл живёт, пока идёт задача, и умирает вместе с ней; между запросами клиента ничего
не тикает. Записано в шапке конфига и модуля, чтобы через полгода это не прочли наоборот.

**`core/providers/task_cycle.py`:** ожидание `trigger → poll → download` + приёмка загрузки.
Интервалы, backoff, пределы и слова-статусы — `config/media_tasks.yaml` с расписанным ЧТО/ПОЧЕМУ/
ЗАЧЕМ: у картинок ожидание секунды, у длинной озвучки минуты, и меняется это чаще, чем код.
В коде цикла нет ни одного слова-статуса — регрессия проверяет грепом.

**Приёмка загрузки — по ДИСКУ, а не по коду ответа.** «200 OK» не означает, что файл лежит:
проверяются существование, ненулевой размер и совпадение с обещанным размером (обрыв на середине
выглядит как успех). Путь проходит containment — ссылка приходит извне, адресу доверять нельзя.
Расширение берётся из строки провайдера (`response_format`), а не угадывается из URL.

**Неизвестный статус** не обрывает ожидание и не выдаётся за успех: копится в отчёте, чтобы после
таймаута было видно, что именно отвечал провайдер.

**Не делали по решению владельца:** пакет задач с параллельным отслеживанием нескольких заданий —
есть в планах, отложено (лимит).

**Приёмка:** `test_providers` 31 → **43/43**, мутации M84 (принимать загрузку без проверки размера)
и M85 (считать неизвестный статус готовностью) краснеют. Гейт 16 passed.

**RESUME:** учёт расхода `current_usage` после вызова — делается БЕЗ живого провайдера и важен:
без него лимиты и fallback остаются теорией, счётчик никто не двигает. Затем сам вызов адаптерами
(нужен поднятый LiteLLM) и пакет задач.

### Сессия 22 (доп. 8) — провайдеры: динамический конфиг, шаг 1 из плана

**Граница, поставленная владельцем:** создание сцены — ДВА разных уровня, и путать их нельзя.
(1) сборка сцены из фрагментов в таблице — это у нас есть; (2) импорт/рендер сцены скриптами
ffmpeg — большая отдельная работа, сейчас НЕ трогаем. Скрипты сцен и анимации не трогаем тоже.
Вместо этого — развёртывание провайдеров через смену моделей и провайдеров динамическим конфигом.

**Шаг 1 сделан: резолвер.** `core/providers/resolver.py` отвечает «кем исполнять `<resource_type>`
прямо сейчас», читая строки листа `RESOURCE_LIMITS` книги канала — того самого, что переехал
из YAML в листы в этой же сессии. Одна строка = провайдер + модель + параметры + лимит + fallback;
адаптер получает всю строку минус служебные столбцы.

**Переключение — `table_update` по строке.** Своего инструмента не завёл: урок этой же сессии —
сперва проверить, не делается ли это существующими дверями. Без кода и без рестарта.

**Что умеет:** порядок строк задаёт основного · исчерпанный `daily_limit` уводит на объявленный
fallback и НАЗЫВАЕТ пропущенного с причиной, а не подменяет молча · `warning_threshold` поднимает
предупреждение, но провайдера не переключает (сигнал, не отказ) · отрицательный лимит = безлимит ·
кольцо `A→B→A` в данных не зацикливает и не врёт про число попыток.

**Ни одного имени провайдера в коде** — регрессия проверяет по границам слова. Первая версия
проверки дала ложное срабатывание: подстрока «Fal» сидит внутри `False`.

**Приёмка:** `test_providers` 23/23 (новый набор), гейт 15 → **16 passed**. Мутации M81 (игнорировать

### Сессия 22 (доп. 6) — сигнал на каждом уровне + долг компенсации (директива владельца)

**Директива:** сигнал нужен не только по тексту, а по КАЖДОМУ источнику — svg-компоненты, музыка,
звуки, переходы. И отдельно: уникальный текст с уникальным фоном МОГУТ закрыть заспамленные
фрагменты, итог пройдёт — но это приём, который нельзя применять раз за разом. Сцене ставится
флаг уровня проекта; при повторении требование ужесточается до новой сцены.

**Сигнал по каждому типу фрагмента.** `fragment_scores` отдаёт оценку по svg_bg, music, transition
и любому объявленному типу отдельно; пороги — `thresholds.per_fragment_type`, тип можно
переопределить поимённо. Прогон: фон 1.0, музыка 0.33 → итог 0.9 выглядит отлично, но сигнал
`critical` с источником `fragment:music`. Раньше такая музыка растворялась в среднем по сцене.

**Компенсация как ДОЛГ, а не как проходной балл.** Если слабое место закрыто сильным соседом,

### Сессия 22 (доп. 5) — слой уникальности A7.2: расчёт есть, и он говорит, хватило ли данных

**Закрыт остаток F30**, который я честно не записывал в закрытие F30: «`scene_profile.enabled=false`
→ тип не входит в формулу уникальности». Исполнено НЕ формулой Excel, а локальным расчётом —
как и решил владелец в S15 (`10 §2`): n-gram/shingling по словам, без внешнего API.
`core/uniqueness` читает профиль типов из ДАННЫХ канала (лист `SCENE_PROFILE`, перенесённый
в книгу в этой же сессии), выключенный тип не входит в композицию вовсе, вес — `niche_weight` оттуда же.

**Главное, чего в дизайне не было, — контракт готовности.** Владелец сформулировал это как
«важны факты: есть ли ВСЕ данные для расчёта или чего-то не хватает». Поэтому любой ответ несёт:
- `readiness`: `full` (все входы, посчитаны все объявленные оценки) / `partial` / `empty`;
- `missing_inputs`: какой оценке какого входа не хватило — поимённо;
- `fragment_gaps`: включённые типы БЕЗ применений.

Последнее — отдельная вещь, которую видно только на прогоне. Сперва такой тип молча давал ноль,
то есть «нет данных» было неотличимо от «повторено целиком». Теперь его вес убирается из
знаменателя (пустота не занижает соседей), а сам он назван в пробелах и делает расчёт неполным.

**Пустой вход даёт объявленный ноль, а не «100% уникально»** — отсутствие текста не достижение.
Неполнота приходит ОТДЕЛЬНЫМ фактом `UniquenessIncomplete`, а не тонет в числе.

**Декларативность проверяется грепом по коду.** В `core/uniqueness/uniqueness_core.py` нет ни
одного типа фрагмента и ни одного порога — регрессия это утверждает. Всё в `config/uniqueness.yaml`:
окно n-gram, метрика, пороги, состав композиции и ОТКУДА брать входы в данных проекта.
Эмпирика анти-D2: смена окна n-gram меняет результат, включение тумблера меняет оценку.

**Источник профиля называется** (`project` / `declaration`): пока книга канала не заполнена, берётся
дефолт из декларации — но выдавать его за настроенный владельцем профиль нельзя.

**Планировщика нет намеренно** (S15): проверку дёргает ИИ инструментом `uniqueness_check`.

**Решение владельца S22 (вопрос был вскрыт прогоном): ХУДШАЯ ОЦЕНКА РЕШАЕТ.** Пороги стоят и на
композиции, и на каждой оценке из `thresholds.per_score`; итоговый уровень — самый тяжёлый из
сработавших, а `alert_sources` называет, ЧТО именно его дало. Иначе провал по одной оценке
закрывался бы соседней хорошей: текст, скопированный слово в слово (0.0), при уникальной сцене
(1.0) давал итог 0.5 и всего лишь `alert`. Теперь тот же случай → `critical`, источник
`script_score`. Мутация M75 (сигнал только по композиции) краснеет 4 проверками.
