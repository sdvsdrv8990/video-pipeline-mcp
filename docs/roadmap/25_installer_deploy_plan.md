# 25 — Установщик с выбором режима и развёртывание

> **Зачем.** `install.sh` сегодня линейный: ставит ВСЁ на одну машину. А ролей две — локальная
> машина (сервер MCP + клиентский конец туннеля) и VPS (только серверный конец туннеля). Нужен
> **выбор режима в консоли** и **динамический конфиг**, который потом сам подхватывает `./run.sh`,
> чтобы одна команда поднимала ровно то, что объявлено ролью.
>
> **Статус: ПЛАН. Кода нет.** Развёртывание серверного конца — это шаги 2–4 плана
> [`24`](24_tunnel_obfuscation_plan.md); здесь — оболочка установки, которая их вызывает.

## Что есть сегодня (проверять запуском, не по этой строке)

- `install.sh` — линейная установка (venv, deps, ffmpeg/onnx-проверки, cloudflared, pre-commit).
- `run.sh` — запуск сервера + туннеля; флаги `--no-tunnel`/`--no-auth`/`--stop`; порт из `VPM_PORT`.
- `scripts/set_provider_key.py` — ввод ключа провайдера СКРЫТО (`getpass`), шифрование, на экран
  только отпечаток (D31: значение не живёт в диалоге). Готовый кусок — вызвать, не переписывать.
- `scripts/models.py` — каталог/установка/запуск локальных моделей (`local`/`install`; STT, bg, upscale).
- `config/tunnel.yaml` — конфиг туннеля (в `.gitignore`, может нести токен).

## Замысел владельца (по смыслу запроса 2026-09-09)

1. Меню выбора режима установки: **локально**, **сервер (только туннель)**, **оба**.
2. Динамический конфиг фиксирует выбор; `./run.sh` подхватывает его без флагов.
3. Режим сервера: скрипт+конфиг шифровки/маскировки пакетов и очистки на уровне сервера, плюс
   вопрос данных сервера / адреса домена (это нормально — outward-facing, спрашиваем интерактивно).
4. Выбор локальных vs онлайн-моделей; для онлайн — печать инструкции вставки токена провайдера
   прямо в консоль (через готовый `set_provider_key.py`), локальные модели ставятся, но
   ЗАПУСКАЮТСЯ инструментами по требованию (`models.py`), а не установщиком.

## Решения этой сессии (владелец, 2026-09-09)

- **Меню — `bash select/read`.** Выбор режима идёт ДО создания `.venv`, поэтому Python-TUI нечем
  запустить (курица-яйцо). Ноль зависимостей, минимум кода — ось 1a. `gum`/`questionary` отвергнуты
  для бутстрапа (лишний бинарь / нет venv). См. вердикты — [`04`](04_github_adoption.md) ось I.
- **Движок серверного туннеля — Xray-core** (VLESS+REALITY), sing-box в резерв. Совпадает с путём Б
  плана 24 (`⟦vpm 0409⟧`).
- **Маскировка — на клиенте, расшифровка — на сервере** (уточнение владельца). Это и есть штатный
  REALITY: локальный конец маскирует+шифрует рукопожатие под TLS к Яндексу, VPS расшифровывает и
  отдаёт наружу чистый трафик. Два конца — ОДИН объявленный поставщик транспорта (Xray) с двумя
  конфигами; см. план 24, раздел «Клиент маскирует / сервер расшифровывает».
- **Секреты вне git (D31).** Трекается только `config/install.yaml` — декларация роли и
  НЕсекретные ручки. Данные сервера, домен, ключи REALITY — в `config/deploy.local.yaml`
  (в `.gitignore`, рядом с `tunnel.yaml`).

## Два этапа (подтверждено кандидатами 2026-09-09)

Стандартный паттерн таких установщиков (ndatg/xray-vless-reality-installer, 0xevn): первый запуск —
УСТАНОВКА, каждый следующий — МЕНЮ управления, без единой команды. Принимаем его:

- **Этап 1 — установка (один раз):** как работать и куда ставить (роль). Голый bash — `.venv` ещё нет.
- **Этап 2 — настройка (меню, БЕЗ команд, повторяемо):** провайдеры/токены/модели. После установки
  `.venv` есть → нормальное Python-меню: выбрал провайдера → вставил токен скрыто, `set_provider_key`/
  `models.py` под капотом. **Нюанс:** ключ провайдера — per-channel (`ChannelSecrets.set(channel,…)`,
  провайдеры из листа `RESOURCE_LIMITS` книги канала), поэтому меню сперва требует канал; модели от
  канала не зависят. На VPS этап 2 = меню управления Xray (добавить клиента, показать конфиг/QR).

## Шаги — отданы плану 26 (решение владельца 2026-09-10)

Сделанное этим планом остаётся на диске: декларация `config/install.yaml`, её читатель
`core/deploy`, ветвление установки по роли и меню настройки `scripts/configure.py`.

Незакрытые шаги (клиентский поставщик Xray, автоподхват в `run.sh`, приёмка) заменены заданиями
владельца 2026-09-10 и живут теперь в [`26`](26_installer_tui_and_tunnel_plan.md) — вместе с
шагами плана [`24`](24_tunnel_obfuscation_plan.md), одним списком вместо двух.

**Что задание 2026-09-10 отменило в решениях выше:**

- **меню — не `bash select`, а `curses`** из stdlib: ноль установки, но стрелки/Enter/Esc и рамки;
  курица-яйцо с `.venv` при этом остаётся решённой;
- **ролей пользователю три — Local · Server · Tunnel**, не `local|server|both`; `both` уходит
  внутрь декларации как техническое значение и на экран не выходит;
- **этап 2 (`configure.py`) перестаёт быть обязательным хвостом установки** — он один из пунктов
  меню после установки; выбор конкретных ИИ-моделей в установщике не делается вовсе.

## Что НЕ делаем этой задачей

- Не трогаем VPS в этой сессии — приёмка сервера и ротация секрета это интерактивный шаг 1
  плана 24, его начинает владелец (`! ssh …`), это outward-facing и его решение.
- Не пишем своё крипто / свою TLS-мимикрию и свой TUI — механизм из библиотеки (ось 1a).
- Не запускаем сторонний root-скрипт установщика целиком — берём его только как источник дизайна
  (см. вердикт `0xevn/xray-reality-setup` в [`04`](04_github_adoption.md)).
- Секреты (ключи REALITY, токены, данные сервера) — вне git.
