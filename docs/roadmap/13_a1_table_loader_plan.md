## Директива владельца (S20) — вывести `channel_config.yaml` в листы и отменить его

**Формулировка:** на канал приходится два конфига — наш и конкурента, по одному принципу. Всё нужное
объявляем в уже существующих шаблонах (таблицы/листы/столбцы); тогда отдельный `channel_config.yaml`
не нужен. Плюс сервер обязан ПРЕДЛАГАТЬ ИИ три режима создания.

### Регрессии в обычном смысле НЕТ — и это проверено

`config/channel_config.yaml` (312 строк, 7 секций) **не читает ни одна строка кода**: по каждой секции
(`workflow_sequences`, `publishing_schedule`, `resource_limits`, `metadata_defaults`, `automation_rules`,
`scene_profile`, `render_config`) — 0 файлов в `core/`, `tools/`, `server.py`, `pipeline/`; единственное
упоминание — комментарий в стабе `ffmpeg_adapter.py:33`. Ломать нечего: у файла нет потребителя.

**Риск не в поведении, а в потере решений.** 312 строк кодируют договорённости (allow-list переходов,
единый источник провайдеров/моделей, «тихий столбец» `scene_profile`). План ниже — сохранение
СОДЕРЖИМОГО, а не тест-план.

### План (порядок, каждый шаг проверяем)

1. **Генератор `config → schema`** — не парсинг прозы, а обход готовой структуры YAML: секция → лист,
   ключи → столбцы, записи → строки-дефолты. Приёмка сильнее, чем у `spec_to_schema`: обратная сборка
   YAML из схемы обязана дать исходный набор ключей и значений (round-trip), иначе конвертация теряет данные.
2. **Флаги столбцов** — `id` для `*_id`/`param`/`fragment_type`/`resource_type`/`metadata_type`;
   остальное `W`. `enabled`/`sync_mode`/`requires_human_approval` — boolean. `severity`/`status`/`action` —
   кандидаты в `enum` (значения взять из фактических данных, не выдумывать).
3. **Куда положить листы — РЕШЕНО (владелец S20): в `channel_data.xlsx`. Имя `channel_config` отменяется
   целиком — и как YAML, и как имя книги.** Правило: **одна книга на сущность**. Два имени на один уровень
   гарантируют путаницу и двойную поддержку; развилка снята намеренно, а не отложена.
   Почему именно `channel_data`: книга уже существует и материализуется (14 листов), это исходное имя от
   дерева файлов, а `_config` — позднее наслоение (ИИ достроил его, когда владелец перешёл на конфиги).
   Переименовывать работающее не нужно — 7 листов конфига просто добавляются к 14 существующим (итого 21).
   Прежнее возражение «человек правит конфиг, сервер пишет данные» снято владельцем: источник правки
   различается на уровне ЛИСТА (`WORKFLOW_SEQUENCES` правит человек, `VIDEOS_INDEX` пишет сервер), и
   этого достаточно — отдельная книга для этого не нужна.
4. **Отмена YAML** — убрать `kind: config` из `channel.tpl.yaml` и удалить `config/channel_config.yaml`
   ТОЛЬКО после шага 1–3 и переноса «РЕШЕНИЙ» из спеки в шапку схемы (пункты 1–5 спеки — это и есть
   ценное содержимое: allow-list-не-маршрут, единый источник провайдеров, sync_mode, «тихий столбец»).
5. **Конкурент — тем же механизмом.** `competitor_channel_data` уже книга; если конкуренту нужен свой
   конфиг, он повторяет ту же схему, а не заводит второй YAML.

**Что при этом НЕ выбрасываем:** механизм `kind: config` (S20) остаётся — doc `10 §5.1` называет вторым
кандидатом на per-project override конфиг умного поиска. Он просто перестаёт обслуживать `channel_config`.

### Три режима создания — сервер обязан ПРЕДЛАГАТЬ (директива S20)

Сегодня `structure_create` молча берёт серверные шаблоны; выбора у ИИ нет и он о нём не знает.
Требуется явная развилка в момент создания:

| Режим | Что делает | Когда |
|---|---|---|
| **default** | ФС + книги из серверных шаблонов «как есть» | обычный случай |
| **custom** | скопировать шаблоны в проект и дать править ДО материализации | у клиента своя структура |
| **manual** | ничего не материализовать, отдать инструменты (`fs_*`, `excel_*`) | нестандартный разовый случай |

Канал передачи — **не** новый параметр в тишине, а `recommendations[]` в ответе (F59: сервер сам
объясняет ИИ разницу). Приёмка: ИИ, не знающий проекта, из ОДНОГО ответа `structure_create` видит все три
режима и чем они отличаются; выбор режима меняет наблюдаемый результат (мутация «убрать режим» → красный).

## Директива владельца (S18-b) — квалифицированный `row_id`: лист + владелец в самом ID (F56)

**Формулировка владельца:** в одной книге несколько листов, в каждом свои строки со своими ID. Запрос
«просмотры конкретного видео» обязан быть однозначным: по ID должно быть видно, **откуда данные и к чему
относятся** — и при записи, и при чтении. На встроенную генерацию полагаться нельзя: структуру ID строки
задаёт **сервер**, и проектируется она **под каждый шаблон индивидуально**.

**Факт сегодня (проверено):** `table_append(..., id_prefix="ROW")` — префикс приходит **параметром от
вызывающего**, то есть его выбирает ИИ; по умолчанию строка получает `ROW_<uuid4hex>`. В ID нет ни книги,
ни листа, ни сущности-владельца. Следствия: два листа дают неразличимые по виду ID; `row_id` из чужого
листа приводит к `ROW_NOT_FOUND` (звучит как «нет такой строки», хотя строка есть — не в том листе);
связь «эта строка про видео VID_…» существует только в голове модели. Плюс префиксы сущностей уже
задвоены (`IDGenerator.PREFIXES` 14 шт. и `template_engine.TYPE_PREFIX` 6 шт. — класс F41/F46);
префиксы листов не должны стать третьим источником.

**Целевая форма (значение самоописательно):**

```
<OWNER_ID>.<SHEET_CODE>.<SEQ>        VID_9f2c…3a.VIEWS.0007
   │            │          └─ порядковый номер строки В ЛИСТЕ (или hex, если нужен параллелизм)
   │            └─ короткий код листа из схемы (VIEWS/SCENES/ASSETS…)
   └─ ID сущности-владельца книги из LinkRegistry (VID_/CH_/COMP_…)
```

**Правила:**
- **Составляет сервер, не ИИ.** `id_prefix` как параметр инструмента уходит: форма берётся из схемы листа,
  владелец — из реестра по книге. ИИ передаёт имена, а не идентификаторы (принцип S17).
- **Объявляется в `.schema.yaml` на каждый лист** — `row_id: {code: VIEWS, strategy: seq|hex}`. Это и есть
  «проектировать под каждый шаблон индивидуально»: блок `row_id` авторится вместе со столбцами листа
  (входит в объём авторинга 6 схем, F20/F21).
- **Разбирается обратно.** Сервер умеет распарсить ID → (owner, sheet, seq) и на чтении/записи проверяет
  соответствие: ID не из этого листа → отдельный код реакции `ROW_SHEET_MISMATCH` с recovery «строка
  принадлежит листу X», а не глухой `ROW_NOT_FOUND`. Ошибка адресации перестаёт выглядеть как отсутствие данных.
- **Совместимость:** старые `ROW_<hex>` остаются валидными (парсер возвращает `owner=None`); миграция —
  по мере перезаписи книг, не разовым переломом.
- **Один источник префиксов:** коды сущностей — из общего реестра префиксов (сведение `IDGenerator.PREFIXES`
  ↔ `TYPE_PREFIX`, F41/F46), коды листов — из схем. Третьего места быть не должно (anti-hardcode).

**Побочный факт, проверенный прогоном (F57):** поиска по ID сегодня нет вовсе, и он молчит.
`QueryPlanner` подмешивает `_row_id` в **выход** (`query_planner.py:246/249`), а фильтрует **раньше**
(`_match_filter` на сырой строке, `:241`) → `filter: {_row_id: {eq: …}}` даёт **0 строк для
существующей строки**. Плюс `table_get_row` требует знать лист заранее. Квалифицированный ID это
и лечит: лист берётся **из самого ID**, поэтому `table_find_by_id(row_id)` — тонкая обёртка над
парсером, без скана и без параметра `sheet`. Вход в B4 вместе с проекцией и `table_update`.

**Приёмка (расширяет E-E «тайминг ID»):** ID новой строки содержит владельца и код листа · тот же ID
возвращается проекцией `table_get_row(columns=[…])` без изменения формы · `row_id` из соседнего листа →
`ROW_SHEET_MISMATCH`, не `ROW_NOT_FOUND` · уникальность в пределах листа при повторных append ·
старый `ROW_<hex>` продолжает читаться · мутация: убрать owner/sheet из формы → тест краснеет.

## Директива владельца (S18-g) — сквозная иерархия ID: сверху вниз, с пропуском уровней (F60/F61/F62)

**Формулировка владельца (три требования):**
1. **Создание объявляет ID заранее.** При создании файла — **неважно, ручного или по шаблону, и неважно,
   созданы уже таблицы или нет** — сервер обязан физически дать ИИ знать, что ID будет присвоен
   автоматически, а по завершении вернуть **имя, адрес и ID** файла (или файлов, если их несколько).
2. **ID строится сверху вниз** — от сетки каналов к каналу и видео: сетка получает свой ID, каждый канал
   внутри несёт ID сетки + свой, каждое видео конкурента — ID сетки + ID канала + свой.
3. **Уровни условны.** Нет сетки (у нашего канала просто один-два конкурента) → сегмент сетки **не
   генерируется**; то же на нижних уровнях. А если есть наш личный канал, к которому привязана сетка, то
   все перечисленные сущности **включая конфиги** получают ещё и ID того личного канала, конкурентами
   которого они считаются. Собрать это в единую систему — в том числе для поиска и в ФС, и в таблицах.

**Факт сегодня (проверено прогонами, F60/F61/F62):**

| Что | Как есть | Следствие |
|---|---|---|
| Шаблонное создание | `TemplateEngine` присваивает `node_id`, `structure_create` пишет в `LinkRegistry` и отдаёт факт `NodeCreated{id,type,name,path,parent_ids}` | единственная здоровая ветка |
| Ручное создание | `fs_create_file`/`fs_write_file`/`fs_create_python_script`/`fs_create_project_structure` — **ни ID, ни записи в реестр**; ответ `{"created": path}` | половина файлов для сервера не существует |
| Предупреждение ИИ | ни одно описание создающего инструмента не говорит про ID (`fs_create_file` = «Создание файла») | ИИ не знает, что адресация по ID вообще есть |
| Форма ID | плоская: `VID_<uuid4hex>` | по ID не видно ни ниши, ни сетки, ни канала |
| Иерархия | живёт в `parent_ids` + в путях | как фильтр поиска недоступна |
| Поиск по ID в ФС | `_extract_id` читает **имя файла**, а ID в имена не попадает никогда | `entity_id=''` у всех; `id_pattern` с реальным ID → **0 результатов** |
| Привязка к нашему каналу | `network.tpl.yaml` декларирует `competitors/{наш_канал}/`, подстановки в движке нет | конкурент лежит в `networks/*/competitors/*`, связь только как ORPHAN-проверка |

**Целевая форма — квалифицированный ID = цепочка предков + собственный сегмент:**

```
NICHE_7d2a01f3/NET_a8c65db6/CH_104e55aa/COMP_3f1b22c9/CVID_9e22aa10
     ниша           сетка        наш канал     конкурент      его видео

нет сетки:        NICHE_7d2a01f3/CH_104e55aa/COMP_3f1b22c9      ← сегмент NET просто отсутствует
книга/конфиг:     NICHE_…/NET_…/CH_104e55aa/FILE_5c0aa731       ← файл наследует цепочку владельца
строка в книге:   CVID_9e22aa10.VIEWS.0007                      ← S18-b: владелец = СОБСТВЕННЫЙ сегмент
```

**Правила:**
- **Собственный сегмент неизменен, цепочка — вычисляема.** Долговременная личность сущности — её
  собственный сегмент (`CVID_9e22aa10`); полная цепочка выводится сервером из `LinkRegistry` при каждом
  ответе. Поэтому появление родителя позже (`structure_link`/`migrate` — конкурент привязан к нашему каналу
  через месяц) **переквалифицирует адрес, не ломая ссылок**. Жёсткое следствие: цепочку **нельзя** хранить
  как внешний ключ — ни в книгах, ни в `read.json`, ни в `row_id`; хранится только собственный сегмент.
- **Пропуск уровня — это отсутствие сегмента, а не заглушка.** Никаких `NET_none`/`NET_-`: нет родителя —
  нет сегмента. Достраивание уровня позже просто удлиняет цепочку.
- **Состав уровней объявляется в `*.tpl.yaml`, под каждый шаблон отдельно** (требование владельца
  «проектировать индивидуально») — новый блок `id:` рядом с `folders`/`files`/`children`:
  ```yaml
  competitor_channel:
    id:
      prefix: COMP                     # единственный источник префикса (снимает F41/F46-дубль)
      parents:
        - { type: channel, required: true,  role: owner_channel }   # наш канал — тот, чьим конкурентом считается
        - { type: network, required: false }                        # нет сетки → сегмента нет
      strategy: scoped8                # 8 hex, уникальность в пределах родителя проверяет реестр
  ```
  Этот же блок — источник для `ENTITY_PATH_PATTERNS` и `REQUIRED_PARENT_TYPE`: сегодня иерархия задана в
  **четырёх** местах (F62), должна остаться в одном.
- **Укорочение сегмента разрешено ТОЛЬКО вместе с проверкой уникальности в реестре.** `strategy: scoped8`
  экономит длину (цепочка из 5 уровней ≈ 65 символов вместо ≈ 200), но лечение D9 держалось именно на
  полной энтропии `uuid4`. Компенсатор — `LinkRegistry.register(check_unique=True)` в пределах родителя с
  ретраем при совпадении; **нет проверки — остаётся `uuid4` целиком.** Обратный разбор принимает обе длины,
  legacy `VID_<32hex>` парсится как цепочка из одного сегмента.
- **Конфиги и книги — тоже узлы цепочки.** `.xlsx`/`.json` регистрируются с `parent_ids=[владелец]` (это
  уже делает `structure_create` для `tables_pending`) и потому автоматически наследуют сегмент личного
  канала. Отдельного механизма «ID для конфига» не заводим.
- **Путь и ID обязаны согласоваться.** Подстановка `{наш_канал}` в контейнере конкурента (объявлена в
  `network.tpl.yaml`, не реализована — F62) делается в том же заходе: сегмент `role: owner_channel` в ID и
  сегмент пути берутся из одного и того же `parent_ids`, иначе получим два расходящихся представления одной
  иерархии.

**Контракт объявления при создании (требование 1) — единый для всех создающих инструментов:**
- В `description` каждого создающего инструмента — фиксированная строка: «ID присваивает сервер; в ответе
  вернутся `name`, `path`, `id` и цепочка владельцев для **каждого** созданного объекта». Это пассивный
  канал из §S18-f, применённый к созданию: ИИ узнаёт про ID **до** вызова, а не после.
- В ответе — единый блок `entities: [{id, type, name, path, chain, owner_id}]` + факт `EntityRegistered`
  на каждый объект. Массив, а не скаляр: файлов может быть несколько (шаблон разворачивает десятки).
- **Независимо от таблиц.** ID присваивается на уровне ФС+реестра, до и без всякой материализации книг;
  книги, созданные позже, ссылаются на тот же ID — именно поэтому `row_id` из §S18-b может встроить
  владельца в себя.
- **Ручная ветка регистрируется тоже.** Файл, созданный вручную внутри `videos/v1/`, получает владельца
  **по вместимости** (ближайший зарегистрированный предок пути) и возвращает `owner_id`. Молчаливое
  «файл вне реестра» исчезает как класс.
- **Собственный ID файла — по запросу (правка владельца S19).** Ранее здесь стояло «файлу собственного ID
  не положено»; владелец решил иначе: ID нужен и ручному файлу, но выдаётся **явным флагом**
  (`assign_id=true`), как и усыновление. Причина та же — контроль: ИИ сам решает, нужна ли файлу личность,
  и **сверяет выданный префикс с классом файла** (`.md`→`MEM`, `.svg`→`AST`, `.xlsx`→`TBL`, `.py`→`SCRIPT`),
  то есть может поймать ошибку генерации, а не принять её на веру. Побочно сохраняется режим «создать без
  ID» — не всякий файл заслуживает записи в реестре. Классы файлов объявлены декларативно
  (`config/templates/workspace/_file_classes.yaml`), в коде префиксов нет. Повторный запрос на уже
  зарегистрированный путь возвращает существующий ID (`reused=true`) — инвариант «один путь = одна
  сущность» из §S18-h держится и для файлов.

**Связка с поиском — один словарь на обе вселенные:**
- ФС: `entity_id` берётся из реестра по вместимости, а не из имени файла (лечит F60 в корне).
- Обе вселенные получают одинаковые фильтры продвинутого поиска (§S18-d/e, со строгой валидацией ключей):
  `owner_id` (всё, что принадлежит сущности) и `chain_prefix` (всё поддерево: `chain_prefix: "NICHE_7d2a01f3/NET_a8c65db6"`
  = вся сетка целиком — файлы, книги и строки). Префиксное совпадение по цепочке заменяет ручной обход дерева.
- Таблицы: владелец в `row_id` (§S18-b) + `chain_prefix` отбирает, какие книги вообще сканировать.

**Приёмка:**
- Создание любым инструментом (ручным и шаблонным) возвращает `entities[]` с `id`/`name`/`path`/`chain`;
  описание инструмента содержит строку про присвоение ID.
- Видео конкурента под нашим каналом даёт цепочку с сегментами ниши/сетки/нашего канала; **тот же
  конкурент без сетки** — ту же цепочку без сегмента `NET_`, без заглушек.
- `structure_link` после факта → цепочка удлинилась, собственные сегменты и `row_id` книг не изменились.
- Поиск: `id_pattern`/`owner_id` по реальному ID возвращает файлы сущности (сегодня — 0, F60);
  `chain_prefix` сетки возвращает и файлы, и строки её видео.
- Путь и ID согласованы: конкурент физически лежит под сегментом нашего канала.
- **Мутации:** убрать сегмент `owner_channel` из цепочки → тест краснеет · вернуть `_extract_id` на разбор
  имени файла → тест поиска по ID краснеет · снять `check_unique` при `scoped8` → тест коллизий краснеет ·
  убрать строку про ID из описания создающего инструмента → тест инвентаря краснеет.

## Директива владельца (S18-h) — цепочка выводится из каталога назначения (F63/F64/F65)

**Формулировка владельца:** создание с нуля вопросов не вызывает. Но когда файл создаётся **в уже
существующей структуре** (наш личный канал, конкурент), сервер обязан **сам понять по каталогу**, какой ID
генерировать: какие уровни сверху вниз пропущены, а какие ID уже готовы и должны быть взяты как есть (ID
канала конкурента, ID личного канала). Пример: «создай видео внутри нашего канала» — сервер должен знать
дерево **конкретного проекта**, где сетки может и не быть. То же для переноса: ID цели присваивается
**до** переноса, чтобы ИИ мог проверить корректность и починить руками, если сервер разложил неверно.

**Факт сегодня (проверено прогонами, F63/F64/F65):**

| Что | Как есть |
|---|---|
| Создание внутрь существующего канала | `structure_create` зовёт движок с `parent_ids=None` **жёстко** (`tools/structure/__init__.py:29`), в схеме инструмента параметра нет → видео ложится по верному пути с `parent_ids=[]` |
| Когда цепочка вообще возникает | **только** внутри одного greenfield-вызова (рекурсия `children`), то есть ровно в том случае, где вопросов и не было |
| Спросить «кто живёт по этому пути» | нечем: у `LinkRegistry` нет `find_by_path` |
| Адресация по (тип, имя) | два `video:intro` в разных каналах → `VALIDATION_ERROR «Неоднозначно»`, ломает `structure_link`/`migrate` |
| Перенос/переименование | мимо реестра; путь протухает, `check_integrity` не сверяет путь с диском → `issues_count = 0` при битом реестре |

**Резолвер — одна функция, оба сценария.** Вход — каталог назначения, выход — вся арифметика цепочки:

```
resolve_chain("niches/gaming/channels/chSolo/videos/") →
  chain:       [NICHE_7d2a01f3, CH_104e55aa]   # взяты ГОТОВЫМИ из реестра
  skipped:     [network]                        # уровень объявлен опциональным, каталога нет
  owner_id:    CH_104e55aa                      # ближайший зарегистрированный предок
  new_segment: {type: video, prefix: VID}       # единственное, что сервер сгенерирует
  unresolved:  []                               # каталоги на диске без записи в реестре
```

**Правила:**
- **Предки берутся готовыми, никогда не перегенерируются.** Каталог, у которого уже есть ID, отдаёт этот
  ID — это и есть «взять готовый ID канала конкурента и личного канала». Молчаливая генерация второго ID
  для существующего каталога — худший из возможных отказов (раздвоение личности), поэтому запрещена явно.
- **Тип нового узла — из шаблона родителя** (`children: [{type: video, container: "videos/"}]`), а не из
  хардкод-карты путей `ENTITY_PATH_PATTERNS` (F62). Дерево конкретного проекта читается из того же
  объявления, которым оно создавалось.
- **Пропуск определяется фактом, а не догадкой.** Уровень объявлен в `id.parents` как `required: false`,
  каталога нет → сегмента нет, и он назван в `skipped`. Отсутствует **обязательный** родитель → узел
  создаётся, помечается ORPHAN (существующий механизм `REQUIRED_PARENT_TYPE`), цепочка просто короче.
  Достроят родителя позже — цепочка удлинится сама (S18-g: цепочка вычисляема).
- **Каталог есть на диске, записи в реестре нет → `unresolved`, а не выдумка.** Усыновление — отдельный
  явный шаг (`structure_adopt` / флаг у создания) с фактом `EntityAdopted`; без него сервер отвечает кодом
  реакции с recovery «усынови предка или укажи другой каталог». Это ровно случай «уже существующая
  файловая система», где реестр отстал от диска.
- **Реестру нужен обратный индекс.** `find_by_path` (F64) + инвариант «один каталог = максимум одна
  сущность своего уровня», проверяемый **при регистрации**, а не постфактум в `check_integrity`.
- **Адресация инструментов — по ID/цепочке.** Имя остаётся человеческой подписью: в иерархии повтор имён
  нормален, и `(тип, имя)` перестаёт быть адресом (F64).

**Предпросмотр — обязательная часть контракта, а не удобство.** `structure_resolve(path)` (readonly, тот же
резолвер) отвечает, какая цепочка получится, какие уровни пропущены и что не разрешилось — **до** создания.
Для greenfield это дублирует S18-g-объявление; для существующей структуры это единственный способ дать ИИ
знать ID заранее, как требует S18-g п.1.

**Перенос (прямое требование владельца):** `resolve_chain(цель)` → показать ИИ дельту цепочки (какие
сегменты меняются, какие уходят) → перенос → `migrate` реестра **в той же операции**; отказ на любом шаге
→ откат до состояния «не переносили». Почему это безопасно чинить руками: собственный сегмент неизменен
(S18-g), поэтому неверная авто-раскладка портит только **адрес**, а не личность — повторный перенос
возвращает всё на место, ссылки и `row_id` не рвутся. Жёсткое следствие: **любая операция, меняющая путь
(`fs_move`/`fs_rename`/`fs_delete`), обязана идти через резолвер** — сегодня они идут мимо (F65), и это
делает цепочку недостоверной для всего поддерева.

**Приёмка:**
- Видео, созданное внутрь существующего канала **вторым вызовом**, получает ту же цепочку, что и созданное
  одним greenfield-вызовом (сегодня — `parent_ids=[]`, F63).
- Канал без сетки: цепочка без сегмента `NET_`, `skipped: [network]`, никаких заглушек.
- Конкурент под нашим каналом при создании получает **готовые** ID канала и сетки, а не новые.
- `structure_resolve` на том же пути отдаёт ровно ту цепочку, которую потом присвоит создание.
- Перенос: до переноса ИИ видит новую цепочку; после — реестр и диск согласованы, `check_integrity`
  краснеет на рассинхроне (сегодня — `0 issues` при заведомо битом реестре, F65).
- Каталог вне реестра → `unresolved` + код реакции, а не тихо сгенерированный новый ID.
- **Мутации:** вернуть `parent_ids=None` в обёртку → тест цепочки краснеет · заставить резолвер
  перегенерировать ID существующего предка → тест «предки берутся готовыми» краснеет · снять `migrate` из
  переноса → тест согласованности реестра с диском краснеет · убрать `unresolved` (усыновлять молча) →
  тест раздвоения личности краснеет.

## Директива владельца (S18-d) — файловый поиск: два инструмента, продвинутый требует фильтры (F58)

**Формулировка владельца:** в файловой системе остаются **два** инструмента поиска — обычный, который
ищет по ID и имени, и второй, который **требует ещё и фильтры**. Мотив: ID в разных проектах могут
совпасть, и тогда поиск по одному ID становится ловушкой — продвинутый вход обязан сузить область.
Общий стиль инструментов файлового домена держим единым.

**Факт (прогон владельца в Claude AI Web + локальное воспроизведение, F58):** сегодня три обёртки над
одной моделью `FsSearchTask` (11 полей), каждая берёт своё подмножество и переименовывает поля
(`root`→`directory`, `extensions`→`extension` ед. ч., `content_keywords`→`keyword`). Фильтры размера/даты
**реализованы и работают** (ядро с `size_min=950` на фикстуре 10×900 Б + 40×1000 Б → ровно 40), но
дотянуться до них можно только через `fs_search_yaml`, чья грамматика описана лишь в docstring
питон-модуля: `input_schema` = `{yaml_query: string}`, `load_query` собирает поля через `data.get(...)`
без валидации → плоский `size_min: 950` молча проглатывается (50 файлов вместо 40).

**Целевая форма:**

| Инструмент | Роль | Вход |
|---|---|---|
| обычный | адресный поиск | `id_pattern`, `name_pattern`, `root`, `limit` |
| продвинутый | сужающий поиск + пакет | те же + `entity_types`, `extensions`, `content_keywords`, `size_min/max`, `modified_after/before`; **минимум один сужающий фильтр обязателен**; принимает список запросов |

**Правила:**
- **Одна Query-модель.** Имена полей = имена `FsSearchTask` (множественные там, где список).
  Переименований в обёртках не остаётся — выученный на одном инструменте паттерн работает на другом.
- **Продвинутый — со схемой, а не со строкой.** `yaml_query: string` уходит: явный `input_schema`
  + `additionalProperties: false`, неизвестный ключ = `VALIDATION_ERROR`, а не тишина. «Требует фильтры»
  выражается схемой (`anyOf` по сужающим полям), то есть проверяется движком до хендлера, а не в коде.
- **Пакетность — свойство, не третий инструмент.** Продвинутый принимает список запросов и идёт через
  `search_parallel`; `fs_search_multi` снимается, и `ThreadPoolExecutor` наконец оказывается у того
  инструмента, чьё описание обещает многопоточность.
- **Выход выравнивается** — один набор полей результата у обоих (сейчас `fs_search_multi` теряет
  `size`/`modified`/`entity_id`/`parent_path`).
- **Расширение нормализуется** (`json` → `.json`): `item.suffix` всегда с точкой, поэтому вариант без
  точки сегодня даёт молчаливый `count: 0`.
- **Описания по факту.** «Очередь, многопоточность» у `fs_search_yaml` — неправда (одна задача, ноль
  потоков); фраза скопирована из табличного домена, где она верна. При правке — сверять описание с кодом.
- **Открытый пункт исполнения:** финальные имена двух инструментов (`fs_search` / `fs_search_advanced`
  или сохранить `fs_smart_search`) — решается при заходе, вместе с `--bless` эталона.

**Приёмка:** один и тот же критерий даёт один и тот же результат на обоих инструментах · `size_min`
реально фильтрует через оба входа · неизвестный ключ → `VALIDATION_ERROR` (не тихий полный результат) ·
запрос без единого сужающего фильтра к продвинутому → ошибка схемы · `extension` с точкой и без даёт
одно и то же · в `test_search` появляются тесты на фильтры (закрывает F55-3) · мутация: снять
`additionalProperties: false` → тест краснеет.

## Директива владельца (S18-e) — табличный поиск: та же пара, что и в файлах (F58, табличная половина)

**Формулировка владельца:** по таблицам тоже должно быть **два** инструмента поиска. Ручные примитивы
адресации (по ID строки, столбцу, листу) остаются — они не «поиск». Умный поиск по таблицам должен идти
**через YAML-запрос ради единого стиля** с файловым доменом. В подписях инструментов обязан быть виден
домен: из списка коннектора не должно быть загадкой, какой поиск про файлы, а какой про таблицы.

**Факт (проверено чтением + git):** болезнь симметрична файловой. Все три табличных инструмента
сводятся к ОДНОЙ модели `QueryPlan`: `search_quick` собирает запрос из одного чтения
(`tools/search/__init__.py:57`), `search_multi` — из N чтений плюс `join` (`:93`), `search_tables`
принимает запрос как есть (`:103`); дальше у всех троих один и тот же
`planner.load_query_from_dict` → `execute_plan`. То есть это три пресета одной модели, а не три
инструмента. `_parse_plan` (`query_planner.py:128`) собирает поля через `data.get(...)` — неизвестный
ключ проглатывается молча, ровно как в файловом домене. **Подписи:** титулы `Поиск: …` не называли
домен; `git show a98cf3b` — они побайтово те же, что до распила `1accee1`, то есть родились
домен-безымянными во внешней search-подсистеме. **Умный поиск по таблицам не терялся** — это
`search_tables`, и он уже принимает оба входа (`yaml_query` строкой и `query_dict` объектом); правда,
`query_dict: {type: object}` без внутренней схемы = тот же молчаливый проглот.

**Сделано сразу (S19):** титулы получили домен — `Таблицы: быстрый поиск`,
`Таблицы: умный поиск (YAML)`, `Таблицы: поиск с объединением (JOIN)`. Файловая тройка сохранила
префикс `Файлы:` — он короче и уже однозначен, а разнобой префиксов внутри одной группы был бы хуже
самой проблемы.

**Целевая форма — зеркальная пара в каждом домене:**

| Домен | обычный | продвинутый |
|---|---|---|
| файлы | по `id_pattern`/`name_pattern` | + сужающие фильтры (обязателен минимум один) + пакет запросов |
| таблицы | одна таблица, один фильтр | запрос целиком: `reads[]`, `join`, `filter`, `sort`, `limit` |

**Правила:**
- **Ручные примитивы остаются и в счёт «двух» не идут.** `table_get_row`/`table_get_column`/`table_set`
  и прочие — адресация по известному ID, а не поиск.
- **`search_multi` поглощается продвинутым.** Доказано кодом: он лишь собирает `reads`+`join` и зовёт
  тот же `execute_plan`; JOIN живёт в `QueryPlan.join`/`_merge_results`, а не в самом инструменте.
  Возможностей не теряется.
- **YAML остаётся — молчание уходит.** «Через YAML для единого стиля» и «не проглатывать мусор» не
  конфликтуют: YAML разбирается, а затем **разобранный объект валидируется против объявленной
  грамматики** (`additionalProperties: false`). Неизвестный или переименованный ключ → `VALIDATION_ERROR`
  с указанием ключа, а не тихий полный результат. Оба входа (строка YAML и объект) — одна схема.
- **Одна грамматика на два домена** там, где смысл общий (`filter`, `limit`, `sort`), и одинаковые имена
  полей внутри домена (см. §S18-d). Выученный на файлах паттерн переносится на таблицы.

**Приёмка:** в списке коннектора каждый поисковый инструмент называет домен · умный табличный поиск
принимает YAML и объект с одинаковым результатом · неизвестный ключ в запросе (оба домена, оба входа) →
`VALIDATION_ERROR` · JOIN-сценарий бывшего `search_multi` воспроизводится через продвинутый без потерь ·
мутация: снять валидацию неизвестных ключей → тест краснеет.

## Директива владельца (S18-f) — сервер сам объясняет ИИ разницу между поисками (F59)

**Формулировка владельца:** сервер обязан давать ИИ чётко понять, **чем инструменты поиска
отличаются друг от друга и в каких случаях какой полезен**.

**Факт: у сервера для этого два канала, и второй не используется вовсе.**

| Канал | Что это | Когда доходит до ИИ | Состояние |
|---|---|---|---|
| описание инструмента | `title` + `description` в `tools/list` | при выборе инструмента | описывает **механизм**, не решение |
| реестр реакций | `recovery.{suggested_tool, suggested_params, reason}` | в момент промаха | **0 из 38 кодов ведёт к поиску** |

Замер реестра: 38 кодов, `suggested_tool` заполнен у 12, **`suggested_params` — у 0**, и **ни один код не
указывает ни на один из шести поисковых инструментов**. Хуже: `ROW_NOT_FOUND` советует ручной скан
(«`table_get_column` отдаст список ID») — то есть в момент, когда ИИ потерял строку, сервер предлагает
перебор вместо поиска, да и то прозой в `reason`, без `suggested_tool`. Описания же говорят про
«очередь, многопоточность» — механизм, из которого невозможно вывести, что брать; у `fs_search_yaml`
это вдобавок неправда (§S18-d).

**Правило 1 — описание описывает РЕШЕНИЕ, а не устройство.** Формат для каждого поискового инструмента:
*что ищет · чем отличается · когда брать · когда НЕ брать (с именем альтернативы)*. Слова «очередь»,
«многопоточность», «параллельно» из описаний уходят: это свойства реализации, ИИ по ним не выбирает.

| Инструмент | Целевое описание |
|---|---|
| файлы, обычный | «Найти файлы по ID или имени. Бери, когда знаешь, что ищешь, и нужен путь. **Не бери**, если отбор идёт по типу/размеру/дате/содержимому или один ID может лежать в нескольких проектах — тогда продвинутый поиск.» |
| файлы, продвинутый | «Найти файлы с отбором: тип сущности, расширение, содержимое, размер, дата модификации. Требует минимум один сужающий фильтр. Принимает несколько запросов за вызов. Бери, когда ответ зависит от свойств файла, а не только от имени.» |
| таблицы, обычный | «Найти строки в ОДНОМ листе одной книги по одному условию. Бери, когда книга и лист известны. **Не бери** для нескольких книг/листов или сведения по ключу — тогда умный поиск.» |
| таблицы, продвинутый | «Запрос по таблицам целиком: несколько чтений, фильтры, объединение по ключу, сортировка, лимит. Вход — YAML или объект той же грамматики. Бери, когда данные нужны из нескольких листов/книг или их надо свести.» |
| примитивы адресации | `table_get_row`/`table_get_column` — **не поиск**: обращение по уже известному ID. Если ID неизвестен, сначала поиск. Это должно быть сказано в их описаниях явно. |

**Правило 2 — каждая ошибка «не найдено» обязана вести к поиску, а не к угадыванию.** Реестр реакций —
активный канал: он попадает к ИИ именно тогда, когда тот заблудился, и именно там сейчас пусто.

| Код | `suggested_tool` | `suggested_params` | Смысл recovery |
|---|---|---|---|
| `ROW_NOT_FOUND` | таблицы, продвинутый | `{table, sheet, filter}` | ищи строку по значению, а не по ID |
| `ROW_SHEET_MISMATCH` (S18-b) | `table_get_row` | `{table, sheet: <из ID>, row_id}` | строка есть — в листе X, перевызови туда |
| `COLUMN_NOT_FOUND` | `json_read_snapshot` | `{table}` | возьми схему листа, не угадывай имя |
| `SHEET_NOT_FOUND` | `json_read_snapshot` | `{table}` | список листов книги |
| `TABLE_NOT_FOUND` | файлы, обычный | `{name_pattern: <имя книги>}` | сперва найди книгу, потом создавай |
| `ENTITY_NOT_FOUND` / `FILE_NOT_FOUND` / `PATH_NOT_FOUND` | файлы, обычный | `{id_pattern \| name_pattern}` | путь ищется, а не подбирается |
| `QUERY_NOT_FOUND` | файлы, продвинутый | `{extensions: [".yaml"], content_keywords}` | найди файл запроса отбором |
| `VALIDATION_ERROR` | — | — | назвать **конкретный** неизвестный ключ и валидное имя (после ужесточения §S18-d/e) |

**Побочно закрывается мёртвое поле:** `Recovery.suggested_params` объявлено в контракте и не заполнено
ни разу (0/38) — класс D2 «декларация без применения». Таблица выше — его первое реальное употребление.

**Приёмка:** у каждого кода семейства NOT_FOUND `suggested_tool` непустой и ведёт к поиску/чтению, а не
к созданию · `suggested_params` непустой у всего семейства NOT_FOUND · описание каждого поискового
инструмента содержит «когда НЕ брать» с именем альтернативы · ни одно описание не содержит слов
«очередь»/«многопоточность» · мутация: убрать `suggested_tool` у `ROW_NOT_FOUND` → тест краснеет.

## Директива владельца (S18) — проекция строк: конфиг оборачивает данные в JSON (F56)

**Формулировка владельца:** «конфиг оборачивает данные из таблицы в JSON — тогда ИИ вносит данные
только когда РЕАЛЬНО пишет значения; в остальных случаях достаточно указать ID строки и нужный
столбец (или несколько), чтобы получить динамические данные из таблицы».

Это продолжение принципа S17 «всё делает сервер, Клод передаёт имена», применённое к строке:
адресация — `row_id` + имена столбцов, форму даёт **схема** (`.schema.yaml`), а не ИИ.

**Чего не хватает сегодня:** проекции нет ни в одну сторону. `get_row` отдаёт строку **целиком**
(`dict(rows[row_id])`, `tables_core.py:122`) — выбрать 2 столбца из 40 нельзя, лишнее едет в контекст;
`get_column` отдаёт столбец целиком; правка идёт по одной ячейке (F56). ИИ вынужден таскать данные
руками там, где мог бы назвать имена.

**Целевой контракт (тонкие обёртки над `tables_core`, логика в ядре):**

| Инструмент | Вход | Выход | Смысл |
|---|---|---|---|
| `table_get_row` (+`columns`) | `row_id`, `columns?: [имена]` | JSON `{column: value}` только по названным (без `columns` — вся строка, back-compat) | чтение без данных от ИИ — только адрес |
| `table_find_row` | `match: {column: value}` | `[row_id]` | адрес по содержимому, а не по памяти ИИ |
| `table_update` | `row_id`, `data: {column: value}` | одна операция в очереди | запись — единственный случай, когда ИИ реально несёт данные |

**Почему через схему, а не «пусть ИИ соберёт JSON»:** типы, `computed`-столбцы и `enum` уже описаны
в `.schema.yaml` — сервер обязан сам отдавать значения в правильной форме (число числом, дата датой,
пусто как `null`, а не строкой «нет данных») и сам отклонять запись в computed. Иначе форма расползётся
по вызовам ИИ = хардкод в промпте вместо декларации (anti-hardcode).

**Экономия контекста — не побочный эффект, а цель:** книга канала — десятки столбцов; вернуть 2 нужных
вместо всей строки уменьшает вход модели на порядок и убирает соблазн «перепиши строку целиком».

**Приёмка:** `table_get_row(columns=[a,b])` возвращает ровно 2 ключа и типы по схеме · неизвестный
столбец → `COLUMN_NOT_FOUND` из реестра реакций (не пустой ответ) · `table_update` пятью полями = ОДНА
операция в очереди · `table_find_row` находит по значению · мутация: убрать проекцию → тест краснеет.

## Директива владельца (S17) — закрывает открытый вопрос

**«Нужно все три»**: интроспектор (F21) + ручной авторинг + F30-деградация. Причина — принцип работы:

1. **Всё делает скрипт, не ИИ.** «Тут не нужны рассуждения, тут всё предельно просто.» Клиент передаёт
   **только имя или имена** (хоть сотню имён конкурентов + «это сетка» + «конкуренты вот этого канала»);
   сущности, книги, имена внутри книг и формулы подставляет сервер. ✅ **Сделано S17:** `structure_create`
   материализует книги сам; пруф — §7 теста (20 конкурентов одним вызовом).
