## 2. Целевая архитектура защиты

```
INBOUND (атакующий → сервер)
  edge (cloudflared): DDoS/WAF/bot — бесплатно always-on, настройки зафиксировать в доке
  ├── auth: fail-CLOSED, identity (не IP)          ← S1
  ├── firewall: IP → rate(identity) → injection → anomaly, все с ЖИВЫМ enabled  ← S0, S4
  ├── лимиты входа: client_max_size, таймауты, строгий JSON-RPC   ← S4
  └── containment путей: safe_resolve (есть) + write-type allowlist  ← S2

OUTBOUND (сервер → Claude AI Web + человек)
  ├── провенанс: workspace-контент помечен как НЕдоверенный, не эхоится в reason/message  ← S3
  ├── деструктив: containment + force-confirm (НЕ destructiveHint)  ← S3
  ├── контракт инструментов только из git (анти-rug-pull), reload не меняет tools/list  ← S6
  └── логи/аудит: без сырого Fact.data, без секретов  ← S3

ИЗОЛЯЦИЯ ХОСТА
  └── не root · нет shell/exec · NoNewPrivileges · cap-drop · read-only rootfs  ← S5

ПРОВЕРКА (иначе этап не закрыт)
  └── unit/contract (T0) · симуляции с чтением консоли (T2) · рой honest+attacker (T6=S7)
```

## 2-бис. Практики, на которые опираемся (S19, проведено через скиллы + внешние источники)

> Директива владельца (S19): планы защиты должны отражать **лучшие и самые надёжные** практики; чего не
> хватает — собрать снаружи. Ниже — то, на что этапы ссылаются нормативно, а не «по памяти ИИ».

| Источник | Что берём | Куда легло |
|---|---|---|
| [MCP Security Best Practices](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices) (нормативный) | **MUST NOT** принимать токены, выпущенные не для этого сервера (token passthrough запрещён) · **MUST NOT** считать владение хэндлом аутентификацией · хэндлы — недетерминированные, привязаны к принципалу · локальный сервер по HTTP **обязан** требовать токен · HTTPS везде, `http` только loopback | S1, S1′, S4 |
| [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization) + [RFC 9728](https://datatracker.ietf.org/doc/html/rfc9728) | OAuth 2.1 + PKCE, сервер = Resource Server; `401` + `WWW-Authenticate` → `/.well-known/oauth-protected-resource`; валидация audience; минимизация scope | S1′ |
| [Claude.ai — custom connectors](https://claude.com/docs/connectors/custom/remote-mcp) | коннектор умеет **OAuth** ИЛИ **Request headers** (фиксированный секрет: `authorization`/`x-api-key`/`x-auth-token`, имена по allowlist, значение хранится и шлётся на каждый запрос) | S1, §3-бис |
| [SlowMist MCP-Security-Checklist](https://github.com/slowmist/MCP-Security-Checklist) + отраслевые гайды 2026 | подпись артефактов сервера и **проверка подписи на старте**; целостность через хэши; version pinning + SBOM + скан зависимостей; `mcp-scan` против отравленных описаний | S6, S8, **S9** |
| Скилл `security-reviewer` (outbound-модель, T1–T7) | ремедиация недоверенного контента = **провенанс и изоляция**, не «распознавание вредных инструкций» | S3 (сделано в S19) |

**Отдельно зафиксировано, что нам НЕ грозит** (чтобы не тащить чужие практики): confused deputy и
token-passthrough не про нас, пока сервер не проксирует третьи API; SSRF из спеки — риск **клиента**,
который ходит по нашим OAuth-метаданным (появится вместе с S1′), а не наш.

## 3-бис. Что умеет клиент (Claude AI Web) — граница возможного

Это ответ на вопрос владельца «как тогда Клод сможет с этим работать». Проверено по докам коннектора:

| Механизм | Claude AI Web | Вывод для нас |
|---|---|---|
| Фиксированный секрет в заголовке (`authorization: Bearer …`, `x-api-key`) | **да** (Request headers, beta; значение хранится у клиента, шлётся на каждый запрос) | **ключ, сгенерированный сервером при установке, работает уже сегодня** — это и есть S1 |
| OAuth 2.1 + PKCE | **да** (штатный путь, вкл. свои client credentials) | S1′ — правильная цель, не «когда-нибудь» |
| Подпись КАЖДОГО запроса ключом (HMAC/Ed25519 по телу) | **нет** — клиент шлёт фиксированное значение, считать подпись по телу он не умеет | request-signing как inbound-защиту **строить нельзя**: не с чем сверять |
| Проверка подписи наших ОТВЕТОВ | **нет** — клиент не верифицирует | подписывать ответы «для клиента» бессмысленно |
| mTLS | не предусмотрено для коннектора | остаётся уровнем туннеля (Cloudflare Access), не приложения |

**Следствие (важное).** Идея владельца «подписывать транзакции и заворачивать чужие» верна, но её место —
**не на входе от Клода**, а на **наших собственных артефактах**: всё, что сервер пишет в `workspace/`
(реестр, очередь, журнал), несёт подпись ЭТОГО инстанса; запись с чужой подписью — или вовсе без неё —
считается посторонней. Тогда второй такой же сервер, другой агент или ручная правка файла перестают быть
невидимыми. Это выносится в новый этап **S9** и не конфликтует ни с S1, ни с S1′ — защита складывается.

## 4. Правила, которые держим

- **Эмпирика вместо гипотез:** находка — только с воспроизведением (PoC, не дальше); `file:line` обязателен.
- **Проводка важнее наличия:** правило считается работающим, если ломается тест при его отключении
  (мутационная приёмка, `tests/CATALOG.md §F`) — иначе это D8 «мёртвое правило».
- **Fail-closed по умолчанию:** битый конфиг → прежние правила (уже так); нет токена → не стартуем (S1);
  неизвестный тип файла → отказ (S2). Тихая деградация в «разрешено» — дефект.
- **Декларативно:** allowlist, лимиты, паттерны — в `config/*.yaml`, не в коде (`anti-hardcode`).
- **Ошибки — через реестр реакций:** каждый новый отказ = код в `server_reactions.yaml` + recovery,
  не сырой текст (`reactions-errors`).
- **Не ломать коннектор:** `destructiveHint` не включаем (auth-гейт Claude.ai) — защита серверная.
- **Безопасность НЕ ищем на GitHub** (`08 §6` ступень B, исключение): механизмы берём из `06`.

## 5. Definition-of-Closed и зрелость

Этап защиты закрыт, когда: (1) механизм построен и **декларативен**; (2) есть тест, который **краснеет при
откате**; (3) симуляция с чтением консоли показывает наблюдаемый эффект (C2 из `08 §6`, требует T2).

| DIM (`07`) | Сегодня | Поднимают |
|---|---|---|
| DIM-2 auth | L0 | S1 → L2, S1′ → L3 |
| DIM-3 sec-inbound | L2 | S0+S4 → L3 |
| DIM-4 sec-outbound | L0 | S3 → L2, S7 → L3 |
| DIM-5 изоляция | L1 | S2 → L2, S5 → L3 |
| DIM-9 supply-chain | L1 | S8 → L2 |
