### Действия за один проход (§6, почему тесты доминируют)
Проход воркстрима = 4 типа работы: **(A)** обмер зоны · **(B)** адаптация готового (кроме sec) ·
**(C1)** простые тесты · **(C2)** симуляции с консолью. Из них C1+C2 — половина и более: реальные
инструменты, живой сервер, чтение консоли, сброс состояния между прогонами. Отсюда вес тестов.

### Сессия 18 (доп. 7) — директива владельца: квалифицированный `row_id` (S18-b, расширение F56)

**Владелец:** в книге несколько листов, у каждой строки в каждом листе свой ID; по ID должно быть ясно,
**откуда данные и к чему относятся** — и при записи, и при чтении. На встроенную генерацию полагаться
нельзя: структуру ID задаёт сервер, и проектируется она **под каждый шаблон индивидуально**.

**Факт:** `table_append(..., id_prefix="ROW")` — префикс приходит ПАРАМЕТРОМ от вызывающего (то есть его
выбирает ИИ), по умолчанию `ROW_<uuid4hex>`: ни книги, ни листа, ни владельца. ID из чужого листа даёт
глухой `ROW_NOT_FOUND` («нет строки», хотя она есть — в другом листе). Префиксы сущностей уже задвоены
(`IDGenerator.PREFIXES` 14 ↔ `template_engine.TYPE_PREFIX` 6 — класс F41/F46); коды листов не должны
стать третьим источником.

**Записано как §S18-b в `13`** (+ «дыра 5» в F56): форма `<OWNER_ID>.<SHEET_CODE>.<SEQ>`
(`VID_9f2c…3a.VIEWS.0007`), составляет СЕРВЕР — owner из LinkRegistry по книге, код листа из
`.schema.yaml` (`row_id: {code, strategy}`), параметр `id_prefix` уходит из контракта. ID разбирается
обратно → проверка принадлежности листу → новый код реакции `ROW_SHEET_MISMATCH` с recovery вместо
`ROW_NOT_FOUND`. Старые `ROW_<hex>` читаются (owner=None), миграция по мере перезаписи книг.
Блок `row_id` авторится вместе со столбцами каждого листа — входит в объём 6 схем (F20/F21).

**Приёмка** расширяет E-E: ID несёт owner+sheet · проекция не меняет форму ID · чужой лист →
`ROW_SHEET_MISMATCH` · уникальность в листе · back-compat · мутация (убрать owner/sheet → красный).

### Сессия 18 (доп. 5) — замечание владельца: редактирование строк таблиц (F56)

**Владелец:** «есть чтение и запись, но нет инструмента редактирования созданной записи; работа со
строкой идёт через row_id, который получаем при записи или прочитав строку; должно работать и через
конфиги, и напрямую — не потерять ручное управление таблицами для ИИ».

**Проверка в коде — ручное управление НЕ потеряно:** `table_set(table, sheet, row_id, column, value)`
и есть правка существующей строки (RMW; валидация листа/строки/столбца + computed-readonly + enum ДО
очереди, применение в `execute_queue`). Но ощущение верное, дыр три:
1. **асимметрия** — `append` принимает словарь, правка одну ячейку → 5 полей = 5 операций в очереди,
   атомарности нет (сбой на середине оставит строку полуобновлённой);
2. **адресация** — `row_id` берётся только из факта `append`, ручного скана `table_get_column` или
   `search_tables`; примитива «найти строку по значению → row_id» нет, хотя весь контракт на row_id;
3. **очередь знает лишь `set|append|delete`** (`push_to_queue` нормализует ровно три) → мульти-полевого
   `update` нет и в декларативном пути: дыра одинаковая напрямую и через конфиг.

**Фикс (F56, блок B4):** `table_update(table, sheet, row_id, data: dict)` — валидация каждого поля +
